# AGENTS.md

Modular-monolith Go boilerplate (`tango`): one binary serving an HTTP/ConnectRPC API, an embedded SPA, and a CLI.

## Project Overview

- Built from `cmd/`. Commands: `serve`, `migrate:up|down|status|version` (plus `migrate:create|reset|seed|validate` in debug builds), `db:export`/`db:import`, `key:generate`/`key:rotate`, `health` (framework: `urfave/cli/v3`). Implemented: `key:generate`, `health`, every `migrate:*`, `db:export`/`db:import`, and `serve` (the basic surface: `/api` landing endpoint, `/api/healthz`, the SPA mount, the metrics exposition, request id and CORS middleware; ConnectRPC routes and the other middleware still wait for their pieces). The rest print `not yet implemented`.
- The SPA (React 19 + TanStack + Vite) builds into `web/output/` and embeds into the same binary. The Vite dev server proxies `/api`, `/rpc`, `/.well-known`, `/static` to the Go server on `:3080`.
- Mid-rebuild. Implemented: `database`, `internal/config`, `internal/datastore`, `internal/health`, `internal/logger`, `pkg/{crypto,envfile,jwtutils,responder,validate,testutils}`, `api/connect`, `email/templates`, `web`. Scaffolds only: most of `internal/**`, all of `modules/**` are single-line packages with no API. Read the file before assuming behavior.
- Never add, remove, or rename a top-level package or directory without an explicit request. Extend an existing package instead.
- Porting a plan or doc into code means implementing it, not copying it. Several docs describe a larger surface than the code has.

## Tech Stack & Tooling

- Go 1.27.1, Node >= 24.21, pnpm 12.5.1, Docker (testcontainers), `task`.
- Target stack: `go-chi/chi`, Postgres via pgx, optional valkey, `samber/do` DI, goose as a library, koanf JSON config, LogLayer Go with `log/slog` as the adapter, OpenTelemetry, S3 + local file storage.
- Optional backends are opt-in, never required: cache defaults to in-memory; session store and rate limit default to Postgres (`public.rate_limits` + `fn_check_rate_limit` under advisory locks). Valkey replaces them only when configured.
- LogLayer (`go.loglayer.dev/v3`, per-transport `go.loglayer.dev/transports/*/v3`): CLI pretty, structured file via lumberjack, OTel. Application code logs through `log/slog`; wire LogLayer as the slog handler (`integrations/sloghandler`), never call LogLayer directly in feature code.
- DI is explicit: constructors registered with `samber/do`, composed in `internal/registry`. No global singletons, no package-level `init`. Use skill `golang-samber-do`.

## Build / Test / Lint

- `task dev` — Vite dev server (:3000) + Go API (:3080). `task run` — Go CLI only, debug build with `--env-file=.env.local`. `task build` — frontend bundle + Go binary. `task start` — run the release binary.
- `task test` — frontend + Go unit tests. `task test:go -- ./modules/...` for one package. `task test:go:debug` covers the `debug`-tagged packages (`./cmd/... ./database/...`).
- `task lint` — golangci-lint + oxlint. `task check` — `go vet` + `migrate:validate` + format check. `task format` — gofmt + oxfmt. `task typecheck` — `tsc -b --noEmit`.
- `task rpc:generate` regenerates Go and TypeScript from `api/connect/*.proto`; `task rpc:stale` fails when the contracts changed without regenerating.
- Task targets wrap the CLI 1:1 (`key:generate` → `go run -tags debug ./cmd key:generate --env-file=.env.local --overwrite`, `db:migrate` → `migrate:up`, `db:rollback` → `migrate:down`, `db:status` → `migrate:status`, `db:version` → `migrate:version`, `db:reset` → `migrate:reset`, `db:create` → `migrate:create`, `db:validate` → `migrate:validate`, `db:seed` → `migrate:seed`, `db:export`/`db:import`, `health`), so a renamed command silently breaks the task. Pass extra flags after `--`.
- `task cert:generate` writes `storage/certs/localhost_{key,crt}.pem` via `mkcert`, falling back to a self-signed `openssl` certificate; `task cert:trust` installs the mkcert CA. The nginx service in `docker/compose.yaml` reads those paths.
- Integration tests use `pkg/testutils.StartPostgres` / `StartMailpit` / `StartMinIO` (testcontainers). They need a Docker daemon: call `testutils.SkipWithoutDocker(t)` so a run without one skips rather than fails (macOS CI has none). Never widen a timeout to work around a hung container.

## Architecture

Implemented today — treat as the contract:

- `database/migrations/` — goose SQL migrations, the single source of schema truth (8 files, `00001`–`00008`). Never embed DDL or create tables at runtime. Editing an applied migration does not re-run it — roll back with `migrate:down` and re-apply. `app_migration` also carries goose's `tstamp` (when a version was recorded), which `migrate:status` reads, so run times need no separate audit table.
- `database/migrator.go` — the engine over goose v3. `NewMigrator` loads the embedded migrations (`go:embed migrations/*.sql`) and builds a `goose.Provider` with a Postgres session locker and `app_migration` as the version table. Migrations run on the single-connection handle from `datastore.OpenMigrationDB`, never the pool. `Up`, `UpTo`, `Down`, `Status`, `Version`, `Pending`, `Applied`, `HighestVersion` return plain structs, so `cmd/` never imports goose. `Down(ctx, count)` rolls back one at a time so goose picks the next in the order it recorded; a version comparison cannot express out-of-order rollback. `MigratorOptions.Progress` receives a `ProgressEvent` per step. goose has no progress hook, so `database/progress.go` translates its verbose slog records (`executing statement` → `started`, `migration completed` → `applied`/`empty`/`rolled back`); only those two, so a goose rename costs the live per-migration line and nothing else, the caller's summary coming from the returned results. Without `Progress`, goose runs a nop logger.
- `database/validate.go` — `Validate` checks the embedded migrations without a database: unparsable file names (goose skips those silently), duplicate or non-consecutive versions, malformed annotations, unbalanced `StatementBegin`/`StatementEnd`, statements outside Up/Down, a file without a Down block. It does not parse SQL. `ValidateFS` runs the same checks over any `fs.FS` so tests use fixtures. `migrate:validate` wraps it and needs no DSN.
- `database/create.go` — `CreateMigration` writes a skeleton at the next version after the highest file on disk, and refuses a name already in use at any version, so the directory never holds two files describing the same change. Names are normalized (lowercase, non-alphanumerics collapsed to `_`), so `"Add Widgets"` and `add_widgets` collide. It creates files, never directories, and validates nothing about the SQL. `MigrationPrefixWidth` is the shared version padding.
- `database/dump.go`, `database/backup.go`, `database/schema_dump.go`, `database/restore.go` — the dump and restore behind `db:export` / `db:import`. Design adopted from `JCoupalK/go-pgdump`, implemented here because that library hardcodes the `public` schema in ~25 queries and reads `information_schema.columns.data_type`, turning `citext` into a literal `citext` with no schema. `dump.go` holds the shared contract: the `public, internal, reference` schema list, `COPY ` header prefix, `\.` terminator, `excludedTables` (`public.app_migration` is migrator bookkeeping, never dumped), `Connector`, `eachRow`. `backup.go` exports on one read-only transaction on one pooled connection, so every COPY sees one snapshot. Rows travel through `PgConn().CopyTo`, never `SELECT` + manual escaping, in `text` format not `csv`: text escapes the terminator, so a value of `\.` cannot end a block, while csv leaves it bare and truncates the table. Each table is ordered by its primary key, so the same state dumps to the same bytes. `schema_dump.go` renders DDL in restore order (schemas, extensions, enums, sequences, tables, constraints, indexes, functions, triggers, comments), one writer per kind, every definition from the server's own deparse helpers (`format_type`, `pg_get_constraintdef`, `pg_get_functiondef`, `pg_get_triggerdef`, `pg_indexes`), never re-derived; extension-owned objects are skipped via `pg_depend.deptype = 'e'`. Every statement is idempotent so a dump replays over an existing schema: `CREATE TABLE`/`INDEX`/`SEQUENCE`/`SCHEMA`/`EXTENSION` take `IF NOT EXISTS`, triggers become `CREATE OR REPLACE TRIGGER`, and `CREATE TYPE` / `ALTER TABLE ADD CONSTRAINT` — no such form exists — are wrapped by `guardedByTypeCheck` / `guardedByConstraintCheck` in a `DO` block that asks the catalog first; drop a guard and `TestSchemaDumpAppliesTwice` fails. Constraints must be ordered globally by type (all PK, then UNIQUE, then CHECK, then FK): per-table order puts `api_keys`' foreign key before `users`' primary key and Postgres rejects it. A catalog query must never run while another query's rows are still iterating on the same connection, or pgx reports `conn busy`; `dumpTables` reads the whole table list before any columns. `restore.go` reads every COPY block into memory, orders the blocks by foreign key (a dump is alphabetical, so a table can precede the table it references), then loads them. `--truncate` empties every table before any row loads, because `TRUNCATE ... CASCADE` would otherwise delete rows already restored. DDL in the file is ignored: the schema comes from `migrate:up`, so a dump cannot disagree with the migrations. A block that ends before its terminator fails rather than importing a partial table.
- `database/compress.go` — the `--compression` container and format detection behind `db:import`. `Compression` is `none|gzip|zlib|zip`, all from `klauspost/compress` — one dependency already in the module graph, so no format is hand-rolled. `pgzip` is deliberately unused: gzip-only, and its parallel writer splits the stream into independent blocks that cost ~7% of the ratio for a speed-up invisible beside the dump's own I/O. The dump is written plain first and compressed after it completes (`CompressFile`), so a failure during the dump cannot leave a half-written archive a reader would accept. A `*zip.Writer` owns its central directory, so `zipEntry` closes the archive, not the entry. Detection reads the file's own bytes (`detectCompression`), never its name: a renamed dump still loads and a name that lies is not believed. A recognized-but-unsupported container (`bzip2`, `zstd`, `xz`, `lzma`, `lz4`) is refused by name via `ErrUnsupportedCompression`; anything else is treated as plain SQL and held to the dump's own contract. zlib is told apart by a valid header (method nibble 8, first two bytes a multiple of 31). `InspectDump` counts blocks and rows for `--dry-run` without a database. **Never read the output buffer before closing the compressor** — the last block is only flushed by `Close`, and reading first yields a silently truncated file.
- `database/seeders/` — the default records a fresh database needs, behind `migrate:seed`. `Seeder` is `{Name, Apply(ctx, datastore.Querier, dryRun)}`; `Name` carries a `Seeder` suffix (e.g. `UserSeeder`, `UserSeederName`) because the report shows it beside the record it created, and a bare entity name would read as the record rather than the code writing it. `All()` returns them in dependency order; `Run` applies each over one querier and wraps a failure with the seeder name. The caller owns the transaction (`cmd/migrate_debug.go` passes `pool.WithTx`), so a failing seeder rolls back everything; the same `Run` works on the pool for a dry run. Every seeder is idempotent and reports the natural key of each record as created or skipped, so a second run is a no-op. `user_factory.go` creates the default account (`admin@example.com` / `@dmin123`, username `admin`, display name `Admin Sistem`, `is_admin`); the password is hashed with `pkg/crypto`'s scrypt hasher and is not computed on a dry run. Inserts use `github.com/huandu/go-sqlbuilder` (`Struct.For(sqlbuilder.PostgreSQL)`) guarded by `ON CONFLICT DO NOTHING`, so a conflict on any unique column keeps the existing row. `UserSchema`/`UserPasswordSchema` and their table constants live in the owning module, not here. `config_factory.go` and `jwks_factory.go` are still empty stubs.
- `modules/identity/<feature>/schema.go` — the table constants and row structs for that feature, so a table rename touches one line and a repository or seeder never hardcodes a name. `db` tags are the column names the query builder reads; structs list only the columns the application writes, so a migration can add a column with a default without touching Go code.
- `cmd/migrate_debug.go` — debug-only commands (`migrate:create|reset|seed|validate`). The actions live here rather than in `cmd/migration.go` because a release build would otherwise compile them into `unused`. `migrate:reset` rolls back everything and, with `--up`, re-applies in one run; on a database with nothing applied, `--up` alone applies the migrations, so `reset --up` also builds a schema from scratch. `migrate:create` takes a `--dir` flag defaulting to `database/migrations` and needs no database. `migrate:seed` first proves the schema is current by asking the migrator for pending migrations, so it refuses with the count and `run migrate:up first` rather than failing halfway on a missing column. A dry run needs no confirmation; a real run asks (unless `--force` or a non-terminal stdin) and runs in one transaction.
- `cmd/migration.go` — DSN resolution and the migration commands. The DSN comes from `envfile.DatabaseURL`, resolved from the root `--env-file` first and the process environment second; nothing else opens a connection. `migrate:up` and `migrate:down` ask for confirmation only when stdin is a real terminal (checked with `golang.org/x/term`, because `/dev/null` is also a character device) and proceed immediately when piped, so `task db:migrate` and CI never block. `up` takes `--to`, `down` takes `--count`; both take `--dry-run` and `--force`. `migrate:status` lists every embedded migration with the time it last ran and closes with the most recent run. `migrate:version` prints the bare version number for scripts and is the only command with no target header.
- `cmd/database.go`, `cmd/database_cmd.go` — `db:export` and `db:import`. Export defaults to `storage/backup/tango-<YYYYMMDD_hhmm>.sql` (UTC) and creates that directory when missing, with or without `--overwrite`: a first run that happens to pass `--overwrite` has nothing to overwrite, so it must not fail for an unrelated reason. A `--output` path the user typed is used as-is and its directory is never created, so a typo stays visible. The generated name is readable to the minute, so a second export inside the same minute would land on the same path; `createExportFile` fails with `ErrDumpFileExists` instead of losing the first dump, and `--overwrite` is the consent. With `--compression` set the guard is on the **final** name (`.sql.gz`), not the plain intermediate, so a stale plain file cannot block a run whose compressed output does not exist yet, and the suffix is appended exactly once. `--force` is the shared confirmation bypass. Import takes the file as a required positional argument (`cli.StringArg{Required: true}`), not a flag, because a restore always has a source. A restore is destructive even without `--truncate` — it replaces rows in the tables the dump carries — so it always confirms unless `--force` is passed; `--dry-run` reports the work and opens no database at all. `printFields` renders a report as labelled values padded to one width, and `reportLabelWidth` pins that width so the target line (before the work) and the summary (after) share one column.
- `cmd/helper.go` — the shared rendering every command builds on, and the one place a spinner is created. One row shape for every migration report: `printMigrationRows` over `migrationRow` (version, state, time, name, duration), so all `migrate:*` reports read alike. `migrationLabel` shortens the row name — the version has its own column and `.sql` says nothing, so `00008_create_scheduler_tables.sql` prints as `create_scheduler_tables` — dropping the prefix only when it is really digits, so `add_widgets.sql` keeps its name; `last run` still names the full file, being a sentence not a row. `migrationStateWidth` sizes the state column from the words a report uses, so `applied` is not padded to a rollback's width while two lists from one command still share a column. `migrationRow.Measured` is separate from `Duration` because a measured zero is a real answer; `migrate:status` shows no duration, the recorded time being when a migration ran, not how long it took. Every outcome line carries a `status:` label at column zero (`printStatusLine`; `printSummary` for the timed closing line), so one `grep '^status:'` finds any command's result. `reportTarget` opens with `database: host:port/name` (never the DSN), so a run against the wrong server shows before it changes anything. A running migration is shown by the spinner, not a row: a row would be overwritten on a terminal and lost in a log. `newSpinner` returns nil off a terminal, so every spinner site is a nil check and a redirected run writes no carriage returns; stop it before the first result row, or its next frame lands at the start of that row. `reporter.restart` begins a second phase in place (`migrate:reset --up`) and must not be replaced by a new reporter: the migrator holds a method value from the reporter, so a new instance would never be called and the second phase would silently keep the first phase's column width and clock. Both halves of `migrate:reset` call it, including the fresh-database path; it lives in `cmd/migrate_debug.go` because `migrate:reset` is debug-only and a release build would otherwise flag it `unused`.
- `pkg/printext` — how output is rendered for a human, shared by the CLI and `internal/health`. It owns colour and formatting. A `Style` names what text means (`StyleOK`, `StyleFail`, `StyleWarn`, `StyleLabel`, `StyleMuted`); a `Palette` decides the colour, so a renderer marks meaning without knowing a colour. `Style` is the vocabulary, `Colour` the four values a palette paints. Formatting: `Duration` (three decimals through `humanize.SIWithDigits`), `Plural`, `PadRight`. Colour is decided per destination, not per process: fatih/color reads `os.Stdout` once at start-up, which is wrong for a writer that is a buffer in a test or a file in a redirected run, so `NewPalette` asks `IsTerminal` and honours `NO_COLOR`. A buffer is never a terminal, so a test sees plain rendering without asking. Pad before colouring, never after: an escape code is invisible but not zero-width to `fmt`, so padding a painted string breaks its column. The package never decides layout — column widths, labels, and which lines a report holds belong to the caller.
- `pkg/crypto` — `Cipher` seals recoverable values with AES-256-GCM and the exact `enc:` prefix; `PasswordHasher` produces PHC strings (scrypt default, Argon2id opt-in). Keys are 32 bytes stored as 64 hex characters (`GenerateKeyHex`, `ParseKeyHex`, `NewCipherFromHex`). `KeyGenerator` always emits all four variables: `APP_SECRET_KEY`, `AUTH_PRIVATE_KEY`/`AUTH_PUBLIC_KEY` as base64 (raw, unpadded) JWK JSON with `alg` and a thumbprint `kid`, and `AUTH_SECRET_KEY`. The key pair and the HMAC secret are independent: defaults `ES256` and `HS256`, and a passed algorithm replaces only the role it can fill (asymmetric → key pair, `HS*` → secret). Passwords are hashed, never encrypted. Do not add another encryption or hashing format.
- `pkg/envfile` — dotenv reader/writer that preserves comments, blank lines, and key order; new files are written `0600`. Owns the `DatabaseURL` key constant (`DATABASE_URL`); pkg/ cannot import internal/, so the config layer derives the same name through `EnvName` and a test asserts the two agree. `key:generate` declares its own `--env-file` flag (the root flag only loads config) and owns the I/O: it only prints unless that flag is given, creates a missing file, and asks before replacing the values of an existing one (`--overwrite` skips the prompt).
- `pkg/responder` — the API envelope, pagination, request IDs (documented in `docs/api-response.md`). `pkg/validate` — request decoding and ozzo v4 code-first validation. Handlers use these; no hand-built envelopes or ad-hoc field guards. `pkg/jwtutils` — JWT signing/verification with typed private claims. `pkg/testutils` — shared testcontainers Postgres, Mailpit, MinIO.
- `internal/datastore` — the Postgres adapter. `NewPostgres` owns the single `pgxpool` of the process (sane pool defaults, connect-time ping, `Ping`/`Stats`/`Close`), `Querier` is the shared pool/transaction surface, and `WithTx` commits when the callback returns nil and rolls back otherwise (including on panic); the callback receives the `Querier`, so a transaction passes to any repository, seeder, or store written against it. Every pooled connection sets `search_path` and `timezone` through `RuntimeParams`, so a recycled connection keeps the same session defaults. `Acquire` hands out a connection for work that must stay on one backend (LISTEN, session advisory locks); callers must release it. ErrNoRows is re-exported so repositories do not import pgx. Migrations never use the pool: `OpenMigrationDB` / `(*Postgres).MigrationDB` return a `database/sql` handle pinned to one connection, because goose holds a session advisory lock and needs every statement of a run on the same backend. `datastore.Valkey` is the key-value backend (`internal/datastore/valkey.go`), on `valkey-io/valkey-go`: `NewValkey(ctx, ValkeyOptions{URL, DB, ApplicationName})` parses the URL with `valkey.ParseURL` (the grammar `isKVURL` mirrors), lets an `opts.DB` of zero or more outrank the index the URL carries, names the connection after the application, and verifies connectivity with a ping before returning — an unreachable backend fails the startup, and a failed construction hands out no client. The ping error carries no target: `RedactKVURL` is the one rendering, applied by the caller. The driver is opt-in: `kvstore.enable` decides availability, and nothing dials the backend while no feature selects it.
- `internal/cache` — the key-value cache drivers, behind one `Cache` contract (`Get(ctx, dst, key)` appends into the caller's buffer — an API designed to be used in zero-allocation mode — plus `Set` and `Del`, each carrying the caller's context, which the remote driver owns a round trip for). `New(cfg, kv)` is the entry point a composition root calls, and Noop is the driver it hands out whenever caching does not run: the cache switched off (`cache.enable` defaults to false — a feature that has not decided to be cacheable cannot grow one by accident), the kvstore driver named while `kvstore.enable` is false (a cache that cannot reach its server is a run without caching, not a broken system — which is why the cache alone among the kvstore features is exempt from `kvStoreDrivers`), or an unknown driver. Noop answers every read with a miss, so a feature never branches on the caching question. `cache_memory.go` is the in-process driver, adopted from `VictoriaMetrics/fastcache` without the dependency: entries are appended into 64 KiB byte chunks (nothing for the GC to scan inside a chunk), an index of `map[uint64]entry` hashes each key with the seeded stdlib `hash/maphash` (per-process seed, so no hash can be crafted offline; `cespare/xxhash` was left unused for this reason), the whole ring is cleaned when the `cache.max_memory` budget is spent while keeping the chunks it grew, and an entry carries its own TTL (`cache.ttl` is the default). Collisions are handled where bigcache overwrites: every entry stores its key, a lookup verifies the bytes before answering, and a colliding entry takes a secondary slot — two keys sharing a hash keep working, only a third evicts the secondary. `Reset` is the only drain the driver takes — the budget, the TTLs, and the ring's own reset already bound what a running cache holds, so there is no flush goroutine to stop. `cache_valkey.go` drives the shared `datastore.Valkey` client: keys are namespaced under `ValkeyKeyPrefix` (`tango:cache:`) — features sharing one server are isolated by prefix, not by logical database index, which Valkey cluster does not support; the backend's memory is the server's business (`maxmemory`, `maxmemory-policy`, per-key TTL) — and any backend failure reads as a miss, because a cache may degrade and the feature behind it may not.
- `internal/health` — the health check engine, adopted in design from `alexliesenfeld/health` but implemented here (no dependency). `NewChecker` takes named checks, runs the due ones concurrently under a global timeout, caches each result for a TTL, recovers a panic into a failure, and aggregates. Two vocabularies on purpose: a component is `up`/`down` (`Status`), the system is `healthy`/`unhealthy` (`GlobalStatus`). `Check.Optional` is reported but excluded from the aggregate, so an optional backend is never an outage; `Check.Target` names what was inspected and appears in the text report. Metadata comes from `WithInfo` (static, such as the build version) and `WithInfoFunc` (computed per call, such as `Uptime`); a static key outranks a computed one. The JSON form is explicit (`marshal.go`) and byte-identical for the same state: durations in milliseconds, details as an ordered array, info with sorted keys, because `encoding/json/v2` does not sort map keys. `Result.Duration` is the length of one check run, not uptime. `WriteText`, `WriteShort`, `Message` are the only renderers, so the CLI and the REST handler cannot drift; `WriteText` takes a `printext.Styler`, pass nil for plain text. The style of a status word is mapped here, in `statusStyle`, because this package owns what `up` and `healthy` mean — `printext` only paints the meaning. `check_postgres.go` and `check_storage.go` hold the checks, `handler.go` the REST endpoint (200/503, standard `pkg/responder` envelope, uncacheable).
- `cmd/healthcheck.go` — the `health` command. It needs no running server: opens the pool, runs the checker, prints the report, exits 3 when unhealthy. `--json` prints the same object the REST handler publishes, `--short` one word, `--timeout`/`--no-cache` tune the run. A database that cannot be reached is a result, not a command error. The Postgres target is rendered from the parsed DSN host/port/database, never the DSN itself, so a report cannot leak the password; the storage target is an absolute path.
- `cmd/logger.go` — how the process logger reaches a command. `initConfig` installs a `loggerState` on the context and the root `After` closes it, so a run flushes what it queued. The logger itself is built **lazily** (`loggerFrom`), not in `Before`: `config:generate` and `key:generate` run before a usable configuration exists, so building eagerly would break the two commands that bootstrap a fresh checkout. The state holds the configuration and a `sync.Once`, so the first command that logs builds one logger and every later call gets the same one. `loggerFrom` reports the failure rather than swallowing it — a command that asked for a logger and did not get one must say so, because the alternative is a run that looks healthy and writes nowhere. `observerState`/`observerFrom`/`closeObserver` live in the same file and work the same way for traces and metrics, because the two have the same lifecycle and the same reason to be lazy; they are separate state so a command that logs does not build a tracer. The root `After` closes the **observer first**, then the logger: a signal drained by the observer may be reported through the logger, and a logger closed first would drop that line. `closeObserver` **reports** a failed drain and returns nil — telemetry is a side channel, so a collector that is down at shutdown means some spans were lost, which is worth saying and is not a reason for a command to exit non-zero. The two shutdown timeouts are separate constants because the metric reader needs longer than a log batch to drain.
- `cmd/loggersmoke.go` — `logger:smoke`. It emits one line per level through every configured transport and prints where each one writes plus the LogsQL query that reads the line back, so the logging path can be proved end to end against a real backend before anything depends on it. It builds the logger itself rather than calling `loggerFrom`, because the command that exists to diagnose logging should not fail before it can say which transport broke. The probe field is named `probe`, not `level`: `level` is the structured transport's own key, and a field of that name would put the same key in the JSON object twice.
- `cmd/otelsmoke.go` — `otel:smoke`. It records one span and one measurement through the providers the configuration enables, and prints what each signal is doing, so tracing and metrics can be proved end to end the way `logger:smoke` proves logging. It goes through `observerFrom`, the same accessor a real command uses, so the run proves the wiring rather than a pipeline assembled for the test. The counts in the closing status line are captured **before** the drain: `Shutdown` releases the providers, so checking afterwards would read every signal as off and report a run that proved nothing as if it had proved something.
- `docker/compose-metrics.yaml` — the observability stack (OpenTelemetry collector, VictoriaMetrics, VictoriaLogs, VictoriaTraces, Perses), included by `docker/compose.yaml`. **The collector is what makes one `otel.endpoint` work**: each Victoria service serves OTLP on its own port, and `docker/otelcol.yaml` fans the three signals out to them, so the application names one address and the routing lives in the collector rather than in the configuration. The paths are the backends' own, not the protocol's: VictoriaLogs serves OTLP on `/insert/opentelemetry/v1/logs` and VictoriaTraces on `/insert/opentelemetry/v1/traces` — **not** `/v1/logs` and `/v1/traces` — and VictoriaMetrics ingests metrics on `/opentelemetry/v1/metrics`. The application ships to the collector's protocol paths and the collector rewrites them, which is why the app config names no path at all. Perses is provisioned from `docker/perses/*.yaml` through the `provisioning.folders` entry in the inline config; those resources are `GlobalDatasource`, not project-scoped `Datasource`, because the config switches project datasources off and this stack has no projects — a project-scoped file is provisioned into nothing and logs `project "default" doesn't exist`. The scrape job for the application points at `host.docker.internal:3080` with `metrics_path: /metrics`; `serve` serves that path once it runs, and the job reports `down` only while `serve` itself is not running. **VictoriaLogs (v1.52) and VictoriaTraces (v0.11) moved their base image from Alpine to distroless**, so neither carries a shell or an HTTP client: an exec healthcheck cannot run at all (`exec: "nc": executable file not found in $PATH`), Docker marks the service unhealthy, and every `depends_on: service_healthy` behind it never starts — Perses stays in `Created` and the stack looks broken while both services are serving. Neither has a flag that probes its own endpoint (`-health` is VictoriaMetrics/VictoriaLogs#1565, still an open pull request, #1741), so the two distroless services carry **no** healthcheck and the services waiting on them wait for `service_started`; the check that matters runs from the host, where curl exists. `metrics:up` ends with `metrics:health`, which probes each endpoint and retries until it answers, bounded by `TIMEOUT` (60s) so a service that never comes up fails the run. Perses answers on `/api/v1/health`, not `/health`. When `-health` ships, reinstate the healthchecks and the `service_healthy` conditions. VictoriaMetrics is still Alpine-based and keeps its own healthcheck.
- `tasks/metrics.yml` — `metrics:up|down|health|endpoints|query|traces|targets|smoke|smoke:otel`, the shortcuts for the stack. `metrics:query` takes a LogsQL query after `--`, `metrics:smoke` runs the logging smoke command with `.env.local`, and `metrics:smoke:otel` runs the trace and metric one. The compose targets stay in the root `Taskfile.yml` next to the compose file they drive; this group only drives the tasks a developer runs while wiring the application to the stack. A Task variable holding a space is quoted into one word, so a loop over several values is written as plain shell inside one `cmd`, not as a Task `for`.
- `pkg/testutils/victorialogs.go` — `StartVictoriaLogs`, the log store container for integration tests, with `Query` and `AwaitQuery` (LogsQL over the query API). One container is shared per test binary, so a test looks for its own marker rather than for an empty store. The wait is an HTTP request on `/health`, not a port check: the port listens before the store can ingest, and a test that shipped to a half-started store would fail on a line that was never written. Shipping is batched, so `AwaitQuery` polls rather than sleeping a fixed time.
- `internal/logger` — the logging stack. One LogLayer core sits behind a `*slog.Logger` (`integrations/sloghandler`), so application code and every dependency that logs through `log/slog` emit into the same pipeline; feature code calls `slog`, never LogLayer. `New(cfg, opts...)` walks `log.transport` in order and builds each named sink: `console`, `file`, `otlp`. The list is what switches a sink on, so there is no second flag that could disagree with it; a name no sink matches fails construction rather than being skipped, and `Validate` refuses an unknown name, a repeated name, and an empty list. The console is the only sink with a rendering choice, carried by its own key `log.console.format` — `pretty` (the `pretty` transport) or `structured` — because what a person reads in a terminal and what a machine reads from a log file are different questions; a file or a collector keeps JSON regardless, has no key to choose, and `Validate` reads the format only when the console is named, so asking for a colourised console cannot put escape codes in the file. Colour is decided per destination (`isTerminal`, the same rule `pkg/printext` applies), so a redirected run and a test buffer stay plain. The threshold lives on the logger (`levelFor`), not on a sink, so every destination agrees on what is worth emitting. `FlattenMetadata` is on, so fields and per-call metadata merge at the root and an entry reads the way slog's own JSON handler writes it. `New` fails rather than degrading — a deployment that asked for a file or a collector and silently got neither has lost the logs it is being trusted with — and `release` closes whatever was built before a later sink failed. `Shutdown` drains the collector first (its batch processor holds queued records nothing else can flush), then releases the file descriptor, and is idempotent. The file sink's path is derived, not configured: `LogFilePath` is `storage.local_path` + `/logs` + `tango.log`, so the process has one data directory and no second path that could disagree with it. The OTLP sink passes **every** exporter option explicitly, including a nil `WithTLSClientConfig` on a plain http endpoint: the exporter otherwise reads `OTEL_EXPORTER_OTLP_*` for its endpoint, headers, compression, and TLS material, which would be a second configuration source deciding what a deployment logs and where, and the resource is built with `resource.NewSchemaless` rather than `resource.Default` so `OTEL_SERVICE_NAME`/`OTEL_RESOURCE_ATTRIBUTES` cannot attribute a record to a service the shell named. The gRPC branch closes the same door with explicit transport credentials rather than `WithInsecure`, because credentials take priority over the insecure and the TLS defaults alike — see `internal/observer` for the full reasoning, which the two packages share. The address is `otel.endpoint` and the resource is built from `otel.service_name`/`otel.environment`, so a record, a span, and a measurement of one service carry the same identity into the same collector. Every entry carries a `source` field (function, file, line): `slog.New` always captures `Record.PC` and `sloghandler` always forwards it, so it is on for every sink without a key of its own — the capture cost is already paid by slog, and a `slog.Record` handed to the handler is a copy whose `PC` can be zeroed by a wrapper if a deployment ever wants the field gone. **`Slog()` is the frontend and the only way feature code writes a line**; the LogLayer core is not exposed — its API is a second way to say what slog says, and using it would split the codebase into two logging idioms, the second of which skips the handler the rest of the stack is wired through. `With(...)` and `WithGroup(...)` are slog's own and work here, because the handler behind the logger implements them: a field added through `With` reaches every later record and a group nests what follows, which is the idiom for request-scoped fields (asserted in `TestSlogChainCarriesFieldsThroughThePipeline`). **Call the `*Context` methods wherever a context is in hand** (`InfoContext`, `WarnContext`, ...): the otellog sink correlates the record with the span the context carries (asserted in `TestSlogContextCorrelatesLogsWithTheActiveSpan`), and a plain `Info` writes a record with no trace ID — logging without the context is what kills log↔trace correlation.
- `internal/observer` — traces and metrics, the two signals `internal/logger` does not own. It follows the logger's shape: the resolved configuration is the only source of truth, each signal is opt-in, and a signal nothing enabled dials nothing. It also owns `exporter.go`, the OTLP exporter plumbing (gRPC credentials, TLS, compression, signal routes) all five exporters of the process share — the logger's log sink imports it rather than carrying a copy, so a decision about what an exporter may read from the environment is made once. `New(ctx, cfg)` returns an `Observer` with every signal off when neither `otel.tracing.enable` nor `otel.metrics.enable` is set, so a caller never checks for nil before `Shutdown`. **Nothing on the request path blocks**: spans go through a batch span processor and measurements through a periodic reader, so recording enqueues and returns, and a collector that is slow, unreachable, or absent costs dropped telemetry rather than a slow request — the queue is bounded by `otel.queue.max_size` and drops the oldest item when full. Metrics leave by **two routes at once**, deliberately: the periodic reader pushes to the collector, and the Prometheus bridge serves the exposition at `otel.metrics.prometheus_path` on the application's own port, which is what the `tango` scrape job in the compose stack reads. `MetricsHandler` exposes the handler for that path; **`internal/transport` mounts it at `otel.metrics.prometheus_path`** on the router it builds, so the compose scrape job reports the service once `serve` runs — a disabled signal mounts nothing, which is why the endpoint is absent rather than empty. The bridge writes into a registry this package owns (`newRegistry`), not the Prometheus default: otherwise a scrape would attribute a dependency's metrics to this service and the Go runtime's collectors would appear on every endpoint. `Observer.Shutdown` stops the metric provider before the tracer provider, and `MetricsHandler` returns nil for a disabled signal rather than exposing an endpoint that reports nothing. `SetGlobals` installs only the enabled providers, so a switched-off signal keeps the SDK's no-op global. The two protocols are separate exporter packages with separate option types, so the exporter is chosen in a branch per signal and there is no shared option list; the branch for a JSON protocol exists only on the trace path, which is the only one the SDK can encode. Like the logger, **every exporter option and every resource attribute is passed explicitly**: the SDK otherwise reads `OTEL_EXPORTER_OTLP_*`, `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`, and `OTEL_SDK_DISABLED`, which would be a second configuration source deciding what this process reports and where. The gRPC exporters read those variables too — `ApplyGRPCEnvConfigs` runs before a caller's options, so a passed option wins — and TLS material is closed the same way at both ends: `grpcTransport` passes explicit credentials rather than `WithInsecure`, because credentials take priority over the insecure and the TLS default alike, and the HTTP path passes a nil `tls.Config` to stop the certificate options from being loaded. `samplerFor` maps `otel.tracing.sampler` onto the SDK samplers, including `parent_ratio` (`ParentBased(TraceIDRatioBased)`), so a service that receives an already-sampled request keeps the trace whole. A route is applied only when the configuration names one or the endpoint carries none: an address that already names a route says where the signal goes, and overriding it with the default would send it elsewhere. The `otel/log` module is pinned at v0.19.0 for the reason recorded below; the trace and metric exporters are on the core version line and stay free.
- `internal/queue` — the embedded task queue, ported from `mikestefanello/backlite` (MIT, SQLite) and owned here: the schema comes from migration `00008_create_scheduler_tables.sql` (the queue and the scheduler state share it), the queries from `go-sqlbuilder` (the seeders' idiom), and the logs from the process `*slog.Logger` the caller passes — the package never builds its own. A `Task` is a payload type whose `Config()` names its queue; `NewQueue[T]` pairs that type with a decoded processor, and `Client.Add(...).Save()` inserts it with a Go-generated UUIDv7, so a caller can reference the task before any commit — `Add` is variadic, which is the batch API: one statement, one transaction. The dispatcher claims with one `UPDATE ... RETURNING` over a `FOR UPDATE SKIP LOCKED` subquery — never claimed, or claimed before `queue.release_after`, and past its `wait_until`, ordered by `priority DESC` then insertion order, so a higher priority is claimed first — so two processes sharing the database never run one task twice, and a lost worker's task is reclaimed. `TaskAddOp.Priority` ranks a task at enqueue time, negative refused; `Client.Cancel` removes a task that has not been claimed yet and reports `false` for one in flight, which finishes its lifecycle. The engine is event-driven: a save notifies it, a delayed task arms the fetcher's ticker, and when nothing is claimable the ticker falls back to one minute — the one bounded poll, which is what makes reclaim independent of traffic. Outcomes: success deletes the task (archiving it in one transaction when the queue's `Retention` asks), a retryable failure releases it for its `Backoff`, an exhausted one archives with the error — the dead letter — and a processor panic is a failure, not a crash; `Dead` counts a queue's dead tasks and `ReplayDead` re-enqueues the ones that kept their payload under a fresh identity, so the archive is a replayable dead letter queue, not a graveyard. When `queue.encrypt` is set the client seals every payload at rest with `pkg/crypto`'s `Cipher` (the `enc:` prefix marks a sealed payload) and opens a claimed payload before the queue decodes it — an in-flight plaintext task from before the flag flipped still runs, and the archive keeps the sealed form so a replay rides the same path. A task whose queue was never registered is re-queued on its own clock and logged — it may be waiting for a deploy — and spends no attempt. `WithTx` callbacks receive the shared `Querier`, so `TaskAddOp.Executor` joins the caller's transaction, and the caller owes it a `Notify()` after the commit.
- `internal/jobs` — the concrete jobs the application runs on the queue: one job per `*_job.go` (task type, `QueueConfig`, processor), with `Register` the one place the queue list is spelled out and the recurring ones seeded, and `Scheduled` the list the cron scheduler enqueues — empty until a feature asks for a cron schedule, because a recurring job that runs on a fixed interval belongs with `Register`, whose self-enqueued successor is durable without a second mechanism. A recurring job keeps its own schedule: its processor enqueues the next instance before returning, and `Register` seeds one only while none is pending, so a restart never multiplies the schedule. `cleanup_job.go` is the first: it purges the completed records their retention has expired, on `queue.cleanup_interval`. The engine's own goroutines know none of the jobs — jobs are application code, the queue is infrastructure.
- `internal/scheduler` — the durable cron scheduler: robfig/cron v3 (zero dependencies) owns the timing, Postgres owns the claim, and the queue owns the execution — a claimed tick only enqueues a task, never runs logic. The state lives in `scheduler_jobs` (migration `00008_create_scheduler_tables.sql`, shared with the queue), one row per job: `next_due` is the claim cursor. Every replica fires the cron time; `fire` opens one transaction that locks the row `FOR UPDATE`, reads the database's own `now()` (so replica clock skew cannot double-fire), advances `next_due` from the old due — a cron spec resumes at its next mark instead of bursting, an `@every` spec catches up one slot per tick — and enqueues the task through `TaskAddOp.Executor` in the same transaction, so a tick is enqueued exactly once and never lost between claim and insert; `Notify` comes after the commit. A failed tick leaves the row untouched and retries at the next firing; the row lock replaces leader election (no elector, no leader lifecycle), and seeding is `ON CONFLICT DO NOTHING`, so a row a deploy created keeps its schedule in motion. `New` refuses a missing store or client, an empty or duplicated name, a nil task, and a spec that does not parse; `scheduler.timezone` resolves a spec that names no zone (robfig's `WithLocation` sets the run loop's clock but not the parser's, so the `TZ=` prefix is prepended and the spec is parsed once).
- `api/connect/*.proto` — ConnectRPC contracts. `email/templates` — React Email sources compiled into `web/email`. `web` — SPA embed and static serving (debug/release variants).

Planned layout — the target shape of the scaffold packages:

- `internal/config` — the configuration layer, on koanf. The JSON config file is the single source of truth: `Load` merges three layers in fixed precedence — built-in defaults, the config file, then the command-line flags. Merge is last-wins per key, not per section, so a source that sets one leaf leaves its siblings alone. **The environment is deliberately not a layer.** A variable reaches a config key only where the file references it, with `env:NAME` as a whole value or `${NAME}` inline, so a user names variables whatever they like, the file decides which key each fills, and a stray export in a shell can never change a value nobody referenced. A directive naming a missing variable is **deferred**, not a load failure: the key keeps its default, `Config.Unresolved` records the variable, and `Validate` reports it only where the missing value leaves the key unusable — so `migrate:status`, which reads only `database.url`, is never blocked by an unset JWT key, and an unset `APP_MODE` falls back to development without an error. The file is **required**: a missing one is `ErrNoConfigFile`, not a fallback to the defaults, so `config:generate` is the first command a fresh checkout runs. `Load` resolves but does not validate, so a command that needs one key is not blocked by a key it never reads; `cmd/config.go` exposes `configFrom(ctx)` for that case and `fullConfigFrom(ctx)` for a command that needs the whole configuration. A duration key is written as a plain number of seconds (`"access_ttl": 900`), never as a duration string: koanf hands a JSON number to mapstructure as a `float64`, which would set a `time.Duration`'s nanoseconds, so `900` would silently mean `900ns`. `internal/config/duration.go` holds `durationKeys`, the list of keys read as seconds; `normalizeDurations` converts a numeric value on those keys only, before each layer is merged. A duration string (`"15m"`) is still accepted, so a hook on the Go type is wrong: a duration is an `int64` and so is an ordinary number. A test asserts `durationKeys` is exactly the set of `time.Duration` fields on `Config`. `app.mode` (not `app.env`) names the runtime mode. The struct is the schema: a field with a koanf and json tag, a default in `Default`, and a rule in `Validate` makes a key work in every source at once. Keys are dotted (`database.max_conns`); `EnvName` is the *convention* the generated file and `.env.example` spell a key as (`DATABASE_URL`), not a loader mapping — deriving it would turn `AUTH_SECRET_KEY` into `auth.secret.key`. A file key that names no config key is dropped, so a stray entry cannot replace a section with a scalar and break the decode. `Sample()` renders the starter file: every key with its default, every key in `secretKeys` as an `env:` directive rather than a literal, and every key in `envKeys` (`app.mode`, `app.base_url`, `app.assets_url`, the `otel.*` deployment keys, the five `mailer.smtp_*` keys, the `kvstore` and `storage.s3` deployment keys) as a directive naming the variable a deployment sets — the name is written out because it does not always match the key upper-cased (`app.base_url` is `PUBLIC_BASE_URL`, and `app.assets_url` is `PUBLIC_ASSETS_URL`). `app.assets_url` names where the browser fetches static assets from: the built-in `/static` mount by default, and an S3 bucket or a CDN origin once a deployment points the variable there — one URL, no driver switch of its own. `log.transport` and `otel.endpoint` are directives, because a deployment is the one that decides whether it keeps the terminal, ships to a collector, or both, and where that collector listens; `log.file.filename` does not exist at all, so there is nothing to pin. A list key written as a directive arrives as one string, because that is all an environment variable can carry, so `internal/config/lists.go` holds `listKeys` and `normalizeLists` splits it (`LOG_TRANSPORT=console,file,otlp`); without that step koanf would decode the string into a one-element list holding "console,file,otlp", which names no sink. A test asserts `listKeys` is exactly the set of slice-valued fields on `Config`, the way the duration test asserts `durationKeys`. The same file holds `mapKeys` and `normalizeMaps` for a key whose value is a map (`otel.headers`), split from the specification's own `name=value,...` form, and the same test asserts it against the map-valued fields. A map key is also kept whole by `flattenNested`, so a **file** writes it as a JSON object rather than as a section: walking it would produce `otel.headers.authorization`, a key that is not part of Config, which `filterKnown` would drop — leaving the header silently unset instead of reported. Space is not a separator: `console file otlp` stays one name and is then refused by name, rather than being read as three sinks nobody asked for. An entry with no `=` is dropped rather than sent as a nameless header, while an empty value (`x-empty=`) is a header with no value, which is legal. `mailer` is the optional email section: an empty `mailer.smtp_host` means the mailer is not configured and is **not** a configuration error, so a local checkout needs no mail server. `Validate` checks only what a set host needs — a usable port, an address in `from_email`, and a username whenever a password is given (`mailer.smtp_password` is a secret, so `Redacted` hides it and `Sample` writes it as a directive). An unset variable is reported only where it leaves the key unusable (`Config.unsetNote`), never for every key that references one: an unset `APP_MODE` falls back to development and `auth.private_key` to the HMAC secret, so reporting those would flag a deliberate choice. Driver and format values are `memory`/`kvstore` (cache), `database`/`kvstore` (rate limit, session), `pretty`/`structured` (log), `local`/`s3` (storage); a key-value backend is named `kvstore` rather than after the product behind it. `storage.s3` holds the object-storage settings, nested rather than flattened because its eight keys cover credentials, the bucket, the endpoint, the addressing style, a prefix, a region, and a link lifetime — a common prefix on each would be noise the nesting already carries. The section is validated **only when `storage.driver` is `s3`**, so a local deployment that keeps credentials in the file for a later switch still runs. `storage.s3.region` has a concrete default (`DefaultS3Region`, `us-east-1`) rather than an empty one because the S3 client refuses to resolve an endpoint without a region and every request fails — even against a service that ignores the region such as MinIO — so an unset `STORAGE_S3_REGION` variable must leave a usable value; an explicitly empty region is still an error. `signed_url_expires` is a duration key, and Validate holds it inside `1s..7d`: the protocol caps a signed link at seven days, and the client reads a zero as "use my own fifteen-minute default" rather than as a lifetime. `force_path_style` defaults to true because MinIO and Silo need it and the client does not fall back on its own (`bucket.localhost` does not resolve). The credentials are in `secretKeys`; their variable names are what `EnvName` derives, so they are deliberately **not** in `envKeys` — that map is for a name that differs from the derived one. `path_prefix` is in `nullKeys`, so a generated file writes `null` rather than `""`; the two resolve alike, so this is about what the file reads like. `log` holds the console settings plus the two optional sinks, selected by `log.transport` — a list of `console`, `file`, `otlp` — which is the one place a sink is switched on. The default is `[console]`, so a fresh checkout and a container that logs to stdout need no volume and no collector. `Validate` refuses a name no sink matches, a repeated name, and an empty list, and checks a section **only when its transport is named**: the rotation keys of `log.file` are read then, and `log.console.format` likewise (the way `storage.s3` is read only on the `s3` driver), including the one combination that never deletes a rotated file (`max_backups` and `max_age` both zero, which would fill a disk quietly), and `log.otlp.path` is held to a path then. `log.file` has no filename key: the sink writes to `storage.local_path + /logs + tango.log`, so the process has one data directory. `otel` is the section the three signals share, and its shape follows from one decision: **one collector address serves logs, traces, and metrics**, because that is what a collector is, so `otel.endpoint` is the only place a collector is named. A signal that needs a different route on that collector sets its own path (`log.otlp.path`, `otel.tracing.path`, `otel.metrics.path`), never its own address — a second address would be a second configuration source deciding where telemetry goes. `otel.endpoint` has a concrete default (`DefaultOTLPEndpoint`, `http://localhost:4318`, the protocol's own port) rather than an empty one, so an unset `OTEL_ENDPOINT` leaves a usable address instead of blocking a deployment whose collector is local, and its scheme is what decides TLS, so there is no second setting to keep in step with it. `otel.service_name` defaults to the application identifier rather than to an empty string, because a record with no service name cannot be attributed at all. `otel.protocol` is shared by the three signals for the same reason the address is: a collector accepts one protocol per listener, so a deployment that needs two is running two collectors, which is what a second address would be. The value is spelled the way the specification spells it, and the endpoint is held to the form the chosen protocol addresses: a URL for the two HTTP protocols, host:port for gRPC. **`grpc` reuses `otel.endpoint`** — the exporter is addressed by host and port, so `CollectorEndpoint` reduces a URL to its host and port and `CollectorSecure` reads TLS from its scheme, which is what keeps one address serving both forms. Switching the protocol without moving the address is refused by name (`DefaultOTELHTTPPort`), because the two protocols are two listeners of one collector: `otel.protocol: grpc` with the default `http://localhost:4318` looks applied and ships nothing. **`http/json` is refused for metrics and logs**, because only the trace exporter encodes JSON in the Go SDK: the alternative is sending protobuf to a collector expecting JSON, which fails somewhere far from the key that caused it. `otel.headers` is a map and therefore in `mapKeys`, so it is kept whole at load time rather than walked into dotted keys `filterKnown` would drop — a JSON object in the file, and the specification's own `name=value,...` string behind a directive. Every header **value** is a secret (in `secretKeys`) because an authorization token is why the key exists and the names inside are chosen by the user; the names are kept in a rendering, since a name says which credential is missing without revealing it. `otel.tracing.*` is read only when `enable` is true, and `otel.metrics.*` likewise, the way `storage.s3` is read only on the `s3` driver: a signal nothing switched on is not held to a sampler or an interval it never runs. `otel.tracing.ratio` is read only by the two ratio samplers, so a ratio outside `0..1` is refused by name rather than silently ignored, and `otel.metrics.prometheus_path` is a **path** rather than a second enable flag: the exposition is always served when metrics are on, and where it is served is the one decision a scrape job needs. `otel.queue.max_size` bounds the in-memory buffer each signal exports from, which is the setting that keeps export off the request path.

`kvstore` is the optional Valkey/Redis section: `Enable` gates availability, while the per-feature driver fields still choose what each feature uses, so switching the backend on moves nothing by itself. `Validate` reports the one combination that cannot work — a driver set to `kvstore` while `Enable` is false — naming every offending driver in one message (`Config.kvStoreDrivers`), and checks `kvstore.url` **only when enabled**, since a disabled backend is never dialled. `isKVURL` mirrors the URL grammar the client accepts (`redis.ParseURL` in `redis/go-redis`: schemes `redis`/`rediss`/`unix`, a missing host defaulted to `localhost:6379`, a path that is empty or one integer database index, a unix socket carrying its path) — validation stricter than the client would reject a URL that connects, and mirroring the query-parameter list is not done because it is a second copy to keep in step. `RedactKVURL` reduces the URL to `host:port/database`; it does **not** reuse `RedactDSN`, whose parse is pgx's and rejects a `redis://` URL outright, which would replace the whole target with the placeholder. There is one data directory, `storage.local_path` — `app.data_dir` was removed rather than kept as a second path that could disagree with it. `secretKeys` is one list, asserted against both `Sample` and `Redacted`, so a secret cannot be written literally or reach a log line. `Config.Origin` reports which layer last set a key (`default` / `config-file` / `flag`). Two secret renderings, deliberately kept apart, both built on `withSecrets`: `Redacted` replaces every secret with `[redacted]` and is the **fail-safe** behind `Config.String()`, so a log line never carries a fragment of a key; `Masked` keeps the first and last four characters with `****` between them, which is what `config:print` renders so a value can be traced to the key that produced it. A secret shorter than `maskMinLength` (16) is redacted in full even by `Masked`, because keeping eight characters of a short password would leave most of it readable; an empty secret stays empty so an unset key reads as unset. Neither renders the DSN: `RedactDSN` reduces it to `host:port/database`, the one rendering the CLI and the health check both use, because a connection string is a composite value where revealing part of the string says nothing. `config:print` renders the resolved configuration as a table (`github.com/rodaine/table`, coloured through `printext.Palette`): the values come from `config.Values(cfg.Masked())`, so a secret cannot reach the table even by mistake, and `--source` adds the layer from `Config.Origin`. It resolves with `configFrom`, **not** `fullConfigFrom`: a configuration being inspected is often one that does not validate yet, so an unset key prints empty rather than stopping the report. The table writes through `trimmedWriter` because rodaine/table pads the last column too, and the header is trimmed **before** it is painted — a colour reset is invisible but not zero-width, so trimming after it would leave the padding inside the escape where it survives into a redirected file. `cmd/config.go` resolves once in the root `Before` and puts the result on the context as a `configState` — the result *and* the failure, because resolution is **deferred**: a broken or absent config file must not stop `config:generate` (writes the file) or `key:generate` (runs before a referenced variable exists), so the command that needs the configuration is the one that reports the error.
- `internal/kernel` — the module contract. A `Module` is `{Name, Mount(chi.Router)}`: it owns its package and registers its endpoints through `Mount`, so no route list outside the module can drift from its handlers. `kernel.Mount` walks the modules a composition root passes; the transport serves what it is given, so a new module needs no change outside `internal/registry`.
- `internal/transport` — the HTTP surface, on chi. `NewRouter` composes the pipeline: request id first (every response and envelope metadata names its request), CORS second (a policy question is answered before a route runs), then the endpoints — the `/api` landing endpoint, `/api/healthz` from `internal/health`, the metrics exposition at `otel.metrics.prometheus_path` when the signal is on, the feature modules' routes, and the SPA mount (`web.SetupStatic`, debug/release variants) last, because its handler answers whatever the routes above it did not claim and its own not-found rule keeps API and protocol paths from being answered with `index.html`. Request ids are TypeIDs with the `req_` prefix (`go.jetify.com/typeid`), honoured from the incoming `X-Request-Id` header and stored through `responder.WithRequestID`, so middleware, envelope metadata, and a later trace agree on one idiom. CORS is `rs/cors` driven by the `server.cors` section; an empty origin list is a passthrough, and `Validate` refuses `*` with credentials because the browser does. `NewServer` binds the timeouts; the listener and the graceful drain stay with `serve`.
- `internal/registry` — the composition root. `New(ctx, cfg, metrics, logger)` registers the shared services with samber/do (config value, the single `datastore.Postgres` pool, the health checker over it, the Valkey client and cache when enabled, the queue client with `internal/jobs` registered on it, the router, the server) and returns the injector; services are lazy, so resolving the server is what opens the pool and an unreachable database fails the run before the listener opens. The metrics handler and the logger come from the caller because both are built and closed by the command lifecycle, not by the container. `serve` starts the queue before the listener opens and closes the injector after the drain — the pool and the workers outlive the listener.

- `modules/<area>/<feature>/` owns one feature: `schema.go`, `repository.go`, `service.go`, `handler_rpc.go` (plus `handler.go` when a REST surface exists), `module.go`. Business logic lives in `service.go`; handlers do transport mapping only. Follow this layout when implementing; do not invent a different file set.
- Persistence goes through `internal/datastore`; never open a second pool or a raw driver connection inside a module.
- Typed IDs come from `go.jetify.com/typeid`; the prefix is declared in the module's `schema.go`. Token and code rows use hashes plus DB `uuidv7()` instead of TypeIDs.
- Background work runs on `internal/queue`: register typed queues, enqueue typed tasks, keep the schema in migrations (`00008_create_scheduler_tables.sql`). Recurring maintenance belongs in `internal/jobs`.

## Library Documentation

- Before writing code against a third-party package, look it up instead of guessing: Context7 MCP (`mcp_context7__resolve_library_id`, then `mcp_context7__query_docs`) for API usage and options, DeepWiki MCP (`mcp_deepwiki__ask_question` with `owner/repo`) for design intent and behavior.
- Use them when the answer depends on a version, when the README is thin, or when comparing two candidate libraries. Do not use them for this repo's own code — read the source.
- The pinned source of truth is the module cache (`go env GOMODCACHE`). When docs and code disagree, the code wins; say so and follow the code.
- The in-memory cache deliberately avoids both cache libraries it was weighed against, so this comparison does not get re-run: `allegro/bigcache` does not handle hash collisions — the new item overwrites the previously stored one, a documented data loss — and `VictoriaMetrics/fastcache` would add `golang/snappy`, `golang.org/x/sys`, and `allegro/bigcache` (its benchmark peer) as runtime dependencies. The design was adopted instead: chunked byte ring, append-style `Get(dst)`, collision handling via full-key verification and a secondary slot. The hash is the stdlib `hash/maphash`, seeded per process; `cespare/xxhash/v2` is already in the module graph (goose, Prometheus) and stays indirect. The key-value client is `valkey-io/valkey-go` over `redis/go-redis/v9` for the same economy: valkey-go brings no runtime dependency beyond `golang.org/x/sys` (already in the graph), parses the `redis://` URL scheme itself via `valkey.ParseURL`, and the `isKVURL` validation mirrors its grammar.
- Record the outcome of a library comparison in this file when it settles a decision, so the next agent does not re-run it.
- The scheduling and concurrency libraries were compared and left out, so this comparison does not get re-run: `go-co-op/gocron/v2` (in-process scheduler, runtime deps `jonboulle/clockwork` + `robfig/cron/v3`) and `alitto/pond/v2` (in-memory worker pool, zero deps). Neither is a queue — both hold everything in memory, so neither can replace `internal/queue`'s durable claim/retry/archive over Postgres, and a process death loses every in-flight task. Recurring jobs need no gocron either: a job that enqueues its own next instance is durable, multi-process safe through the queue's atomic claim, and inherits retries, backoff, and archive — what an in-process scheduler provides only behind an elector or locker that has to be implemented and run somewhere. Revisit gocron only when cron-expression schedules (daily at a time, monthly) become a real requirement, and even then the durable shape is a cron parser that computes the next run and enqueues it as a task, never business logic running in-process.
- River (`riverqueue/river`) was evaluated for the same questions and left out, so this comparison does not get re-run: a mature Postgres queue, but adopting it would replace `internal/queue` wholesale — its own schema (`river_job`, `river_job_state` enum, `river_leader` election, `river_migration` versioning), its own client/worker idiom, and a dependency set beyond pgx (`pgerrcode`, `puddle`, `tidwall/gjson`+`sjson`, `x/sync`) — for features tango has not asked for. The parts that would tempt later are a paid Pro subscription ($125/mo, private module): workflows, batching, sequences, concurrency limits, dead letter queue, durable periodic jobs (`Pilot` persistence), encrypted jobs, ephemeral jobs. Its periodic-job shape validated the `internal/scheduler` design instead: a `Next(time)` schedule interface with robfig/cron plugged in as the implementation, an atomic claim so exactly one replica triggers a tick (River runs the enqueuer on an elected leader; a CAS claim on `scheduler_jobs` needs no election), and claim + enqueue in one transaction. Worth porting when a real need appears: unique jobs via a partial unique index, and queued-task cancellation.
- The LogLayer transports are version-pinned as a set, and `otellog` is the reason. `go.loglayer.dev/transports/otellog/v3` v3.0.0 was built against `go.opentelemetry.io/otel/log` v0.19.0, where `Record.Body()` returns `otellog.Value` and attributes are `otellog.KeyValue`. OTel moved `KeyValue` and `Value` into `go.opentelemetry.io/otel/attribute` in `otel/log` v0.20.0, so the transport does not compile above v0.19.0 (`undefined: otellog.StringValue`). `go.opentelemetry.io/otel/exporters/otlp/otlplog/otlploghttp` and `go.opentelemetry.io/otel/sdk/log` are held at v0.19.0 for the same reason: their `otel/log` floor has to agree with the transport's. The core module (`go.opentelemetry.io/otel`, and `otel/sdk` with it) is on its own version line and stays free, and so are the trace and metric exporters (`otlptracehttp`, `otlpmetrichttp`, `exporters/prometheus`), which depend on the core module rather than on `otel/log`. Before bumping any of the three pinned modules, check that the transport still compiles; the failure is at the type level and shows up only when `otellog` is built. **`go get` on an unrelated OTel package will silently raise `otel/log` past the pin** — it happened while adding the metric exporter — so after any `go get`, re-check the three versions and `go mod edit -require` them back.

## Conventions

- Config precedence, lowest to highest: built-in defaults → JSON config file → CLI args. `internal/config` is the only place this order is implemented — a command reads the resolved value from the context (`configFrom` / `fullConfigFrom` in `cmd/config.go`), never `os.Getenv` or a flag directly. The environment is a **value table the file references**, not a layer: adding a key does not add a variable, and exporting a variable nobody referenced changes nothing.
- A flag reaches the configuration only through `flagBindings` in `internal/config/flags.go`, and only `serve` has one (`--host`, `--port` → `server.*`, `--base-url` → `app.base_url`). A flag is for a setting a user tries for one run; a flag that changes what a command does (`--dry-run`, `--force`) must never be listed. `storage.local_path` has no flag and no variable of its own: it comes from the file alone, so a run cannot disagree with the configuration about where files live.
- Interpolation is how a secret stays out of the file: `${NAME}` inline, `env:NAME` as a whole value. Both read the system environment, plus a `--env-file` when one is named (which wins for a name both set). Only the file is interpolated — a variable's own value is data, so a DSN containing `$` survives intact.
- Every config key needs a default in `config.Default`, a rule in `config.Validate`, and — when it is a secret — a line in `secretKeys` so `Sample` writes it as a directive and `Redacted` hides it. `.env.example` is the file `docs/deployment.md` pipes into `fly secrets import`, so it carries the secrets plus the deployment variables (`APP_MODE`, `PUBLIC_BASE_URL`, `PUBLIC_ASSETS_URL`, the `envKeys` set) that `Sample` also writes as directives; any other non-secret default belongs in the config file, not there.
- One file per stage of a Config's life, so a new function has one obvious home: `types.go` (the shape), `defaults.go` (the built-in values and the constants they use), `keys.go` (the flat key space), then one file per source — `file.go`, `env.go`, `flags.go` — and `validate.go` for everything done to a Config after it is resolved, including `Redacted`/`RedactDSN`/`String`. `config.go` holds the package doc, `Options`, and `Load`. Do not add a file for a single function: a constant belongs beside the defaults that reference it, and a redaction beside the validation that is its counterpart.
- Go 1.27 idioms: `encoding/json/v2` (with `omitzero`), `for range n`, `t.Context()` in tests, `errors.Join`, `slices`/`maps`, `min`/`max`, stdlib `uuid`.
- Shut down through context cancellation: servers, queue workers, background jobs stop in order and drain in-flight work. New long-running components must implement stop.
- Comments are for what the code cannot say: an invariant, security rule, protocol requirement, or side effect. Write them short and functional. Never add a comment that only restates the code, narrates control flow, or repeats a name. Never leave phase/task/plan markers or signatures such as `phase *`, `Step N`, `TODO(plan)`. Mark real future rework with a `TODO` or `FIXME` saying what to change and why.
- Do not add compatibility shims, fallback readers, or dual-write paths. Delete the obsolete path instead.
- Fix lint findings at the source. `//nolint` is not an accepted answer.
- Command output: pluralize counts through `printext.Plural` (never `%d migration(s)`), humanize durations through `printext.Duration`, indent per-item lines and leave outcome lines at column zero under a `status:` label so `grep '^status:'` works, and print a `database:` target line before touching anything. A command a script parses prints only its value (`migrate:version`). Colour and formatting come from `pkg/printext`, never from a command's own helper, and `--json` output is never coloured.

## Common Tasks

- Add a feature module: create `modules/<area>/<feature>/` with the standard file set, implement the `internal/kernel` module contract in `module.go`, register it in `internal/registry`.
- Add an endpoint: write the proto in `api/connect/*.proto`, run `task rpc:generate`, implement the handler, mount it in the registry.
- Add a migration: run `task db:create -- add_widgets` (or `go run -tags debug ./cmd migrate:create add_widgets`). It writes `database/migrations/<NNNNN>_<name>.sql` at the next free version and refuses a name another migration already uses. Every migration must define both `-- +goose Up` and `-- +goose Down` (goose requires one `Up`; the CLI's `migrate:down` requires the `Down`). The version must be `>= 1`, exactly 5 digits, consecutive with the previous file, and higher than the last; `migrate:create` maintains all four, and a hand-written file must follow the same rules. goose treats version 0 as the sentinel row and silently skips a file numbered below 1, so a `00000_*.sql` file never runs and never errors — bump the version assertions in the migrator tests when adding one. Migrations are embedded, so a new file only runs after a rebuild; `go run` and the Taskfile rebuild on every call. Run `task db:validate` to check the files without a database.
- Add a seeder: add a factory file in `database/seeders/` returning a `Seeder` and append it to `All()` in dependency order. Name it after the code, not the entity — `<Entity>Seeder` (e.g. `UserSeeder`). Put table constants and row structs in the owning `modules/<area>/<feature>/schema.go`, not in the seeder. Make `Apply` idempotent — guard every insert with `ON CONFLICT DO NOTHING` and report an existing record as skipped. Never open a connection: `Apply` receives a `datastore.Querier` and the command owns the transaction.
- Add a dump object kind: add one writer to `dumpDDL`'s section list in `database/schema_dump.go` and place it where a restore needs it. Prefer the server's own deparse helper (`pg_get_*`, `format_type`) over assembling the definition in Go, and skip extension-owned objects through `pg_depend.deptype = 'e'`. Read the whole list before querying anything per item: a nested query on the same connection fails with `conn busy`. Add the case to the round-trip test in `database/backup_test.go` that applies a schema dump to an empty database — that check catches a statement written in the wrong order.
- Add a test that touches the schema: get a database per test with `testutils.StartPostgres(t).NewDatabase(t)`. The shared container DSN points at one database for the whole test binary, so migrations applied by one test leak into the next. A test needing two databases (a dump source and a target) may call `NewDatabase` twice; each call gets its own database.
- Add a config key: define it in `internal/config` with a default and validation, add it to `secretKeys` when it is a secret, honor the precedence order above. Map a flag to it in `flagBindings` only if it genuinely needs a flag. Do not add a variable for it: a key is reachable from the environment only where a file references it.
- Add a background job: define the task type, its `QueueConfig`, and its processor in a new `internal/jobs/<name>_job.go`, and register the queue in `internal/jobs/register.go` so the composition root picks it up. A recurring job re-enqueues its own next instance; enqueue from the owning module or handler through the `queue.Client` the registry provides.
- Add a log sink: add the name to the `LogTransport*` constants and `LogTransports()` in `internal/config/types.go`, give its section a default and a rule in `Validate` (read only when `log.transport` names it), then build it in `internal/logger` and append the transport to the walk in `New`. Hold anything that owns a resource in a small sink struct so `Shutdown` can release it — a file descriptor, a queue — and join its error rather than replacing the one that stopped construction. A sink that cannot be built is an error, never a silent downgrade to the console. Add the case to `TestEveryTransportShipsTheSameEntry` in `internal/logger/integration_test.go`, which is the check that one entry reaches every named sink.
- Prove a logging change end to end: `task metrics:up`, then `LOG_TRANSPORT=console,file,otlp task metrics:smoke`, then `task metrics:query -- 'marker:"tango-logger-smoke"'`. The store is shared, so the query names the marker rather than looking for an empty store. The integration test does the same thing against a testcontainer (`testutils.StartVictoriaLogs`), so a change to the shipping path is covered without the compose stack running.
- Prove a tracing or metric change end to end: `task metrics:up`, then `OTEL_TRACING_ENABLE=true OTEL_METRICS_ENABLE=true task metrics:smoke:otel`, then `task metrics:traces` for the service name and `curl -s --get --data-urlencode 'query=tango_otel_smoke_total' http://localhost:8428/api/v1/query` for the measurement. Both go through the collector, so the run proves the fan-out and not just the exporter. `internal/observer/observer_test.go` covers the same ground against an `httptest` collector, so the pipeline is tested without Docker.
- Add a signal setting: it belongs in the `otel` section when it describes where the collector is or what the service is (shared by all three signals), and in the signal's own subsection when only that signal reads it. Never add a second collector address — a signal that needs a different route sets a path. Add the key to `internal/config`, a default, a rule in `Validate` (read only when the signal is on), and a line in `envKeys` when a deployment sets it.
- Local services: `docker compose -f docker/compose.yaml up -d pgsql` for the database; the full stack (pgsql, redis, mailpit, silo, nginx) plus the observability services is in `docker/compose.yaml`, which includes `compose-metrics.yaml`. `task metrics:up` starts only the observability half.

## Gotchas / Anti-patterns

- `codegen/` is gitignored build output. Never edit or commit it; regenerate with `task rpc:generate`.
- Task targets live in `tasks/*.yml`, one file per group, each included with `flatten: true` so a task keeps the name it had when the root file held it: `task db:migrate`, never `task database:db:migrate`. Flattening also keeps one flat namespace, so a task in one file can depend on a task in another by its plain name (`deps: [rpc:generate]`) — a prefixed include cannot see a flattened name. Add a group by writing `tasks/<group>.yml` and adding a flattened include to the root `Taskfile.yml`; do not add a task to the root file. Root `vars` (`APP_NAME`, `APP_VERSION`, `IMAGE`) are inherited by every included file.
- The `compose:*` targets are the one exception and stay in the root `Taskfile.yml`, next to the `docker/compose.yaml` they drive. Do not move `docker/compose.yaml` into `tasks/`; it must stay at the repository root.
- `task` (the default) runs `task --list` without `--sort none`: flattened includes have no declared order, so `--sort none` prints the groups in a different order on every run. Alphabetical order keeps each group together because every task carries its group as a name prefix.
- Tool configs live in `.config/` (`golangci.yml`, `goreleaser.yaml`, `lefthook.yml`, `ncurc.json`, `sql-formatter.json`), **except the two oxc configs**, which must stay at the repository root. Which tools find a config in `.config/` on their own was measured, not assumed: golangci-lint, goreleaser, and lefthook discover it and need no flag; `ncu` needs `--configFilePath .config --configFileName ncurc.json`. Do not move `.oxfmtrc.json` or `.oxlintrc.json` into `.config/`: both resolve `ignorePatterns` **relative to the config file's own directory**, so from `.config/` every root-anchored pattern (`/codegen/**`, `*.md`, `/index.html`) silently stops matching and the tools start scanning the whole tree. `../` is rejected outright — the config fails to parse. oxfmt and oxlint auto-discover a config in the root, so they need no flag there either. After moving a config, re-check its `$schema` path, which is relative to the config file.
- The root `--env-file` flag adds a dotenv file to the table the config file's directives resolve from; it is not a config layer, and it is never a write target. A subcommand that writes a file (`key:generate`) must declare its own flag of that name, or `task run -- <cmd>` would rewrite `.env.local`.
- `app.config.json` is required and is the single source of truth, so a command that has to run before it exists cannot resolve the configuration. Resolution is therefore deferred: `initConfig` stores the result *and* the failure on the context, and only the command that reads it reports it. Never move resolution back into a hard failure in `Before` — it would break `config:generate` and `key:generate`.
- Never print a literal secret. `config:generate` writes an `env:` directive, and `Redacted`/`RedactDSN` cover every rendering path; both read the one `secretKeys` list, so a new secret is added there and nowhere else.
- Keep the README lean — setup steps, task table, certificates, deployment, license — and free of architecture detail. The "Implemented today" list in this file and the code are the source of truth for what runs; update that list when a scaffold package becomes real. Do not re-add architecture tables, emoji, or per-path inventories to the README.
- Do not require valkey, S3, or SMTP for the default local path; Postgres plus local storage must be enough.
- Never rewrite a dotenv file the user owns without consent: print instead, or ask first. Destructive overwrite needs an explicit flag.
- Do not run destructive database commands (`migrate:reset`, volume removal) against a database holding state you did not create.
- A command whose action prints `not yet implemented` is not implemented. Never document, test, or rely on it as working, and never report a stub path as validated.

## Committing

- Stage explicit paths only; never `git add -A` / `git add .`. Verify with `git status` before committing.
- Message format: `{feat,fix,docs,refactor,chore}[(scope)]: <concise message>`.
- Never push. Commits are local unless the user asks for a push.
- Never commit on your own initiative — finish the work, recommend a message, and let the user commit. The exception is an explicit commit instruction in that turn.
- Always close a finished piece of work with a recommended commit title in chat, even when you did not commit. Use the format above, keep it one line, and list the changed paths under it.

Never run: `git reset --hard`, `git checkout .`, `git clean -fd`, `git stash`, `git commit --no-verify`, `git push --force`.
