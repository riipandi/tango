# AGENTS.md

Modular-monolith Go boilerplate (`tango`): one binary serving an HTTP/ConnectRPC API, an embedded SPA, and a CLI.

## Project Overview

- The binary is built from `cmd/` and exposes `serve`, `migrate:up|down|status|version` (plus `migrate:create|reset|seed|validate` in debug builds), `db:export`/`db:import`, `key:generate`/`key:rotate`, and `health` (CLI framework: `urfave/cli/v3`). Implemented: `key:generate`, `health`, every `migrate:*` command, and `db:export`/`db:import`; the rest print `not yet implemented`.
- The SPA (React 19 + TanStack + Vite) builds into `web/output/` and embeds into the same binary; the Vite dev server proxies `/api`, `/rpc`, `/.well-known`, and `/static` to the Go server on `:3080`.
- The backend is mid-rebuild. Implemented today: `database` (migrations + engine), `internal/datastore`, `internal/health`, `pkg/{crypto,envfile,jwtutils,responder,validate,testutils}`, `api/connect`, `email/templates`, and `web`. Scaffolds only: most of `internal/**` and all of `modules/**` are single-line packages with no API. Read the file before assuming behavior.
- Never add, remove, or rename a top-level package or directory without an explicit request. Extend an existing package instead of creating a sibling one.
- Porting a plan or a doc into code means implementing it, not copying it. Several docs describe a larger surface than the code has.

## Tech Stack & Tooling

- Go 1.27.1, Node >= 24.21, pnpm 12.5.1, Docker (testcontainers), `task` (`Taskfile.yml`).
- Target stack: `go-chi/chi` router, Postgres via pgx, optional valkey, `samber/do` DI, goose as a library, koanf JSON config, LogLayer Go with `log/slog` as the adapter, OpenTelemetry, S3 + local file storage.
- Optional backends are opt-in, never required: cache defaults to in-memory, session store and rate limit default to Postgres (`public.rate_limits` + `fn_check_rate_limit` under advisory locks). Valkey replaces them only when configured.
- LogLayer: `go.loglayer.dev/v3` with per-transport modules (`go.loglayer.dev/transports/*/v3`) — CLI pretty, structured file via lumberjack, and OTel. Application code logs through `log/slog`; wire LogLayer as the slog handler (`integrations/sloghandler`) instead of calling LogLayer directly in feature code.
- DI is explicit: constructors registered with `samber/do`, composed in `internal/registry`. No global singletons, no package-level `init` wiring. Use skill `golang-samber-do` when using `samber/do` DI.

## Build / Test / Lint

- `task dev` — Vite dev server (:3000) + Go API (:3080). `task run` — Go server only, debug build with `--env-file=.env.local`.
- `task build` — frontend bundle + Go binary. `task start` — run the release binary.
- `task test` — frontend + Go unit tests. `task test:go -- ./modules/...` for one package. `task test:go:debug` covers the `debug`-tagged packages (`./cmd/... ./database/...`).
- `task lint` — golangci-lint + oxlint. `task check` — `go vet` + `migrate:validate` + format check. `task format` — gofmt + oxfmt. `task typecheck` — `tsc -b --noEmit`.
- `task rpc:generate` regenerates Go and TypeScript from `api/connect/*.proto`; `task rpc:stale` fails when the contracts changed without regenerating.
- `task key:generate` runs `go run -tags debug ./cmd key:generate --env-file=.env.local --overwrite`; `task db:migrate` runs `migrate:up`, `db:rollback` runs `migrate:down`, `db:status`/`db:version` wrap the matching commands, `db:reset` runs `migrate:reset`, `db:create` runs `migrate:create`, `db:validate` runs `migrate:validate`, `db:seed` runs `migrate:seed`, `db:export` runs `db:export`, `db:import` runs `db:import`, and `health` runs `health`. Pass extra flags after `--`.
- `task cert:generate` writes `storage/certs/localhost_{key,crt}.pem` via `mkcert`, falling back to a self-signed `openssl` certificate; `task cert:trust` installs the mkcert CA. The nginx service in `compose.yaml` reads those paths.
- Integration tests use `pkg/testutils.StartPostgres` / `StartMailpit` / `StartMinIO` (testcontainers). They need a Docker daemon; call `testutils.SkipWithoutDocker(t)` when one may be absent (macOS CI has none).
- Check library documentation before writing code against a third-party package: use the Context7 MCP (`mcp_context7__resolve_library_id` then `mcp_context7__query_docs`) for usage and options, and the DeepWiki MCP (`mcp_deepwiki__ask_question`) for design intent and behavior questions about a GitHub repository. See "Library Documentation" below.

## Architecture

Implemented today — treat as the contract:

- `database/migrations/` — goose SQL migrations, the single source of schema truth (9 files, `00001`–`00009`). Numbering starts at 1: goose reserves version 0 as the sentinel row in `app_migration`, and silently skips any file whose numeric prefix is below 1. Never embed DDL or create tables at runtime. Editing an applied migration does not re-run it — roll back with `migrate:down` and re-apply. `app_migration` also carries goose's `tstamp` column (the moment a version was recorded); `migrate:status` reads it, so a migration's run time is available without a separate audit table.
- `database/migrator.go` — the migration engine over goose v3. `NewMigrator` loads the migrations embedded in the binary (`go:embed migrations/*.sql`) and builds a `goose.Provider` with a Postgres session locker and `app_migration` as the version table. Migrations run on the single-connection handle from `datastore.OpenMigrationDB`, never the pool. `Up`, `UpTo`, `Down`, `Status`, `Version`, `Pending`, `Applied`, `HighestVersion` return plain structs so `cmd/` never imports goose. `Down(ctx, count)` rolls back one migration at a time, so goose picks the next in the order it recorded — a version comparison cannot express out-of-order rollback. `MigratorOptions.Progress` receives a `ProgressEvent` per step as it happens; goose has no progress hook, so `database/progress.go` translates its verbose slog records (`executing statement` → `started`, `migration completed` → `applied`/`empty`/`rolled back`). Only those two records are translated, so a goose rename costs the live per-migration line and nothing else — the caller's summary comes from the returned results. Without `Progress` goose runs with a nop logger, because the command prints the results itself.
- `database/validate.go` — `Validate` checks the embedded migrations without a database: unparsable file names (which goose skips silently), duplicate or non-consecutive versions, malformed annotations, unbalanced `StatementBegin`/`StatementEnd`, statements outside Up/Down, and a file without a Down block. It does not parse SQL. `ValidateFS` runs the same checks over any `fs.FS` so the tests use fixtures. `migrate:validate` wraps it and needs no DSN.
- `database/create.go` — `CreateMigration` writes a new migration skeleton. It takes the next version after the highest file on disk and refuses a name that is already in use, whatever version carries it, so the directory never holds two files describing the same change. Names are normalized (lowercase, non-alphanumerics collapsed to `_`), so `"Add Widgets"` and `add_widgets` collide. It creates files, never directories, and validates nothing about the SQL. `MigrationPrefixWidth` is the shared version padding.
- `database/dump.go`, `database/backup.go`, `database/schema_dump.go`, `database/restore.go`, `database/compress.go` — the SQL dump and restore behind `db:export` / `db:import`. Adopted in design from `JCoupalK/go-pgdump` (query the catalog, emit DDL) but implemented here, because that library hardcodes the `public` schema in ~25 queries and reads `information_schema.columns.data_type`, which turns `citext` into the literal `citext` without its schema. `dump.go` holds the shared contract: the `public, internal, reference` schema list, the `COPY ` header prefix and `\.` terminator, `excludedTables` (`public.app_migration` is the migrator's bookkeeping and is never dumped), the `Connector` interface, and `eachRow`. `backup.go` is the exporter: one read-only transaction on one pooled connection, so every COPY sees the same snapshot. Rows travel through `PgConn().CopyTo`, never `SELECT` + manual escaping. The format is `text`, not `csv`: in text format the server escapes the terminator, so a value that is `\.` cannot end a block, while csv leaves it bare and truncates the table. Each table is ordered by its primary key, so the same state dumps to the same bytes. `schema_dump.go` renders the DDL, one writer per object kind, in restore order: schemas, extensions, enums, sequences, tables, constraints, indexes, functions, triggers, comments. Every definition comes from the server's own deparse helpers (`format_type`, `pg_get_constraintdef`, `pg_get_functiondef`, `pg_get_triggerdef`, `pg_indexes`), so nothing is re-derived. Objects owned by an extension are skipped through `pg_depend.deptype = 'e'`, because `CREATE EXTENSION` already creates them. Every statement is idempotent, so a dump replays over an existing schema: `CREATE TABLE`/`INDEX`/`SEQUENCE`/`SCHEMA`/`EXTENSION` take `IF NOT EXISTS` and triggers become `CREATE OR REPLACE TRIGGER`. Postgres has no `IF NOT EXISTS` for `CREATE TYPE` or `ALTER TABLE ADD CONSTRAINT`, so `guardedByTypeCheck` and `guardedByConstraintCheck` wrap those two in a `DO` block that asks the catalog first. Add a statement without a guard and `TestSchemaDumpAppliesTwice` fails. Inside the constraints section the order must be global by type (all PK, then UNIQUE, then CHECK, then FK): ordering per table puts `api_keys`' foreign key before `users`' primary key and Postgres rejects it. A catalog query must never run while another query's rows are still iterating on the same connection, or pgx reports `conn busy`; `dumpTables` reads the whole table list before it reads any columns. `restore.go` is the importer: it reads every COPY block into memory, orders the blocks by foreign key (a dump is alphabetical, so a table can precede the table it references), and loads them. Reading first is what makes the FK-safe order possible. `--truncate` empties every table before any row is loaded, because `TRUNCATE ... CASCADE` would otherwise delete rows already restored. DDL in the file is ignored: the schema comes from `migrate:up`, so a dump cannot disagree with the migrations. A block that ends before its terminator fails rather than importing a partial table.
- `database/seeders/` — the default records a fresh database needs, behind `migrate:seed`. `Seeder` is `{Name, Apply(ctx, datastore.Querier, dryRun)}`; `Name` carries a `Seeder` suffix (e.g. `UserSeeder`, `UserSeederName`) because the report shows it on the same line as the record it created, and a bare entity name would read as the record rather than the code that writes it. `All()` returns them in dependency order and `Run` applies each over one querier and wraps a failure with the seeder name. The caller owns the transaction (`cmd/migrate_debug.go` passes `pool.WithTx`), so a failing seeder rolls back everything — the same `Run` works on the pool for a dry run, which has nothing to roll back. Every seeder is idempotent and reports the natural key of each record as created or skipped, so a second run is a no-op rather than an error. `user_factory.go` creates the default account (`admin@example.com` / `@dmin123`, username `admin`, display name `Admin Sistem`, `is_admin`); the password is hashed with `pkg/crypto`'s scrypt hasher and is not computed on a dry run. Inserts are built with `github.com/huandu/go-sqlbuilder` (`Struct.For(sqlbuilder.PostgreSQL)`) and guarded by `ON CONFLICT DO NOTHING`, so a conflict on any unique column keeps the existing row. `UserSchema`/`UserPasswordSchema` and their table constants live in the owning modules, not here. `config_factory.go` and `jwks_factory.go` are still empty stubs.
- `modules/identity/<feature>/schema.go` — the table constants and row structs for that feature, so a table rename touches one line and a repository or seeder never hardcodes a name. `db` tags are the column names the query builder reads; structs list only the columns the application writes, so a migration can add a column with a default without touching Go code.
- `cmd/migrate_debug.go` — debug-only commands (`migrate:create|reset|seed|validate`). The actions live here rather than in `cmd/migration.go` because a release build would otherwise compile them into `unused`. `migrate:reset` rolls back everything and, with `--up`, re-applies it in one run; on a database with nothing applied, `--up` alone applies the migrations, so `reset --up` also builds a schema from scratch. `migrate:create` takes a `--dir` flag defaulting to `database/migrations` and needs no database. `migrate:seed` first proves the schema is current: it opens the migration handle and asks the migrator for pending migrations, so it refuses with the count and `run migrate:up first` rather than failing halfway on a missing column. A dry run needs no confirmation, a real run asks (unless `--force` or a non-terminal stdin) and runs in one transaction.
- `cmd/migration.go` — DSN resolution and the migration commands. The DSN comes from `envfile.DatabaseURL`, resolved from the root `--env-file` first and the process environment second; nothing else opens a connection. `migrate:up` and `migrate:down` ask for confirmation only when stdin is a real terminal (checked with `golang.org/x/term`, because `/dev/null` is also a character device) and proceed immediately when piped, so `task db:migrate` and CI never block. `up` takes `--to`, `down` takes `--count`; both take `--dry-run` and `--force`. `migrate:status` lists every embedded migration with the time it last ran and closes with the most recent run, `migrate:version` prints the bare version number for scripts and is the only command with no target header.
- `database/compress.go` — the `--compression` container and the format detection behind `db:import`. `Compression` is `none|gzip|zlib|zip`, all from `klauspost/compress` (`gzip`, `zlib`, `zip`) — one dependency already in the module graph, so no format is hand-rolled. `pgzip` is deliberately not used: it is gzip-only, and its parallel writer splits the stream into independent blocks that cost ~7% of the ratio for a speed-up that is invisible next to the dump's own I/O. The dump is always written plain first and compressed after it completes (`CompressFile`), so a failure during the dump cannot leave a half-written archive a reader would accept; the entry name inside a zip is also known before the archive is opened. A `*zip.Writer` owns its central directory, so `zipEntry` closes the archive rather than the entry. Detection reads the file's own bytes (`detectCompression`), never its name: a renamed dump still loads and a name that lies is not believed. A recognized-but-unsupported container (`bzip2`, `zstd`, `xz`, `lzma`, `lz4`) is refused by name via `ErrUnsupportedCompression`; anything else is treated as plain SQL and held to the dump's own contract. zlib is told apart by a valid header (method nibble 8 and a first-two-bytes multiple of 31), which is what keeps ordinary text from being mistaken for it. `InspectDump` counts blocks and rows for `--dry-run` without a database. **Never read the output buffer before closing the compressor** — the last block is only flushed by `Close`, and reading first yields a silently truncated file.
- `cmd/database.go`, `cmd/database_cmd.go` — `db:export` and `db:import`. Export defaults to `storage/backup/tango-<YYYYMMDD_hhmm>.sql` (UTC) and creates that directory when it is missing, with or without `--overwrite`: a first run that happens to pass `--overwrite` has nothing to overwrite, so it must not fail for an unrelated reason. A `--output` path the user typed is used as it is and its directory is never created, so a typo stays visible. The generated name is readable to the minute, so a second export inside the same minute would land on the same path; `createExportFile` fails with `ErrDumpFileExists` instead of losing the first dump, and `--overwrite` is the consent. With `--compression` set the guard is on the **final** name (`.sql.gz`), not the plain intermediate, so a stale plain file cannot block a run whose compressed output does not exist yet, and the suffix is appended exactly once. `--force` is the shared confirmation bypass. Import takes the file as a required positional argument (`cli.StringArg{Required: true}`), not a flag, because a restore always has a source. A restore is destructive even without `--truncate` — it replaces rows in the tables the dump carries — so it always confirms unless `--force` is passed; `--dry-run` reports the work and opens no database at all. `printFields` renders a report as labelled values padded to one width, and `reportLabelWidth` pins that width so the target line (printed before the work) and the summary (printed after) share one column.
- `cmd/helper.go` — the shared rendering every command builds on, and the one place a spinner is created. Every migration report is one row shape, built by `printMigrationRows` from a `migrationRow`: version, state, time, name, and duration, so `migrate:up`, `migrate:down`, `migrate:status`, and both halves of `migrate:reset` read as the same report instead of dialects of it. `migrationLabel` shortens the name for the row — the version has its own column and `.sql` says nothing, so `00009_add_session_remember.sql` prints as `add_session_remember`; the version prefix is dropped only when it really is digits, so a file named `add_widgets.sql` keeps its name. The full file name is still what `last run` names, because that is a sentence rather than a row. `migrationStateWidth` sizes the state column from the words a report actually uses, so an apply (`applied`) is not padded to the width of a rollback (`rolled back`), while two lists printed by one command still share a column. `migrationRow.Measured` is separate from `Duration` because a measured zero is a real answer — a migration with no statements takes no time — and `migrate:status` shows no duration at all, since the recorded time says when a migration ran, not how long it took. Every outcome line carries a `status:` label at column zero (`printStatusLine`, and `printSummary` for the timed line that closes a run), so `grep '^status:'` finds what any migration command did without a pattern per command. `reportTarget` opens with `database: host:port/name` (never the DSN) so a run against the wrong server is visible before it changes anything; `reporter` draws one row per finished migration from the engine's `Progress` events and times the run; `printSummary` closes with a pluralized count and a humanized duration. Rows are indented and the summary is not, so the summary is greppable at column zero. A migration still running is shown by the spinner, not by a row: a row would be overwritten on a terminal and lost in a log. `newSpinner` returns nil when the writer is not a terminal, so every spinner site is a nil check rather than a branch, and a redirected run writes no carriage returns into its log. A spinner must be stopped before the first result row is written, or its next frame lands at the start of that row and the two run together. `reporter.restart` begins a second phase in place (`migrate:reset --up`), and must not be replaced by a new reporter: the migrator holds a method value taken from the reporter, so a new instance would never be called and the second phase would silently keep the first phase's column width and clock. `restart` is called by both halves of `migrate:reset`, including the fresh-database path where only the up half runs, and lives in `cmd/migrate_debug.go` because `migrate:reset` is debug-only and a release build would otherwise compile it into an unused method.
- `pkg/printext` — how output is rendered for a human, shared by the CLI and `internal/health`. It owns two things. First, colour: a `Style` names what a piece of text means (`StyleOK`, `StyleFail`, `StyleWarn`, `StyleLabel`, `StyleMuted`) and a `Palette` decides the colour, so a renderer marks its output without knowing a colour. `Style` is the vocabulary; `Colour` is the four values a palette can paint. Second, formatting: `Duration` (three decimals through `humanize.SIWithDigits`), `Plural`, and `PadRight`. Both were duplicated before — `internal/health` and `cmd` each had their own duration renderer — which is the drift this package exists to stop. Colour is decided per destination, not per process: fatih/color reads `os.Stdout` once at start-up, which is wrong for a command whose writer is a buffer in a test or a file in a redirected run, so `NewPalette` asks `IsTerminal` and honours `NO_COLOR`. A buffer is never a terminal, so a test sees the plain rendering without asking. Pad before colouring, never after: an escape code is invisible but not zero-width to `fmt`, so padding a painted string breaks the column it was meant to hold. The package never decides layout — column widths, labels, and which lines a report holds belong to the caller.
- `pkg/crypto` — `Cipher` seals recoverable values with AES-256-GCM and the exact `enc:` prefix; `PasswordHasher` produces PHC strings (scrypt default, Argon2id opt-in). Keys are 32 bytes and stored as 64 hex characters (`GenerateKeyHex`, `ParseKeyHex`, `NewCipherFromHex`). `KeyGenerator` always emits all four variables: `APP_SECRET_KEY`, `AUTH_PRIVATE_KEY`/`AUTH_PUBLIC_KEY` as base64 (raw, unpadded) JWK JSON with `alg` and a thumbprint `kid`, and `AUTH_SECRET_KEY`. The key pair and the HMAC secret are independent: defaults are `ES256` and `HS256`, and a passed algorithm replaces only the role it can fill (asymmetric → key pair, `HS*` → secret). Passwords are hashed, never encrypted. Do not add another encryption or hashing format.
- `pkg/envfile` — dotenv reader/writer that preserves comments, blank lines, and key order; new files are written `0600`. Owns the `DatabaseURL` key constant (`DATABASE_URL`) so the CLI and future config layer cannot drift. `key:generate` declares its own `--env-file` flag (the root flag only loads config) and owns the I/O: it only prints unless that flag is given, creates a missing file, and asks before replacing the values of an existing one (`--overwrite` skips the prompt).
- `pkg/responder` — the API envelope, pagination, and request IDs (envelope documented in `docs/api-response.md`). `pkg/validate` — request decoding and ozzo v4 code-first validation. Handlers use these; no hand-built envelopes or ad-hoc field guards.
- `pkg/jwtutils` — JWT signing/verification with typed private claims. `pkg/testutils` — shared testcontainers Postgres, Mailpit, MinIO.
- `internal/datastore` — the Postgres adapter. `NewPostgres` owns the single `pgxpool` of the process (sane pool defaults, connect-time ping, `Ping`/`Stats`/`Close`), `Querier` is the shared pool/transaction surface, and `WithTx` commits on a nil callback and rolls back otherwise (including on panic). Every pooled connection sets `search_path` and `timezone` through `RuntimeParams`, so a recycled connection keeps the same session defaults. `Acquire` hands out a connection for work that must stay on one backend (LISTEN, session advisory locks); callers must release it. `ErrNoRows` is re-exported so repositories do not import pgx. Migrations never use the pool: `OpenMigrationDB` / `(*Postgres).MigrationDB` return a `database/sql` handle pinned to one connection, because goose holds a session advisory lock and needs every statement of a run on the same backend. `internal/datastore/valkey.go` is still a stub.
- `internal/health` — the health check engine, adopted in design from `alexliesenfeld/health` but implemented here (no dependency). `NewChecker` takes named checks, runs the due ones concurrently under a global timeout, caches each result for a TTL, recovers a panic into a failure, and aggregates. Two vocabularies on purpose: a component is `up`/`down` (`Status`), the system is `healthy`/`unhealthy` (`GlobalStatus`). `Check.Optional` is reported but excluded from the aggregate, so an optional backend is never an outage; `Check.Target` names what was inspected and appears in the text report. Metadata comes from `WithInfo` (static, such as the build version) and `WithInfoFunc` (computed per call, such as `Uptime`); a static key outranks a computed one. The JSON form is explicit (`marshal.go`) and byte-identical for the same state: durations in milliseconds, details as an ordered array, and info with sorted keys, because `encoding/json/v2` does not sort map keys. `Result.Duration` is the length of one check run, not uptime. Durations go through `humanize.SIWithDigits` (three decimals), the same rendering the migration report uses. `WriteText`, `WriteShort`, and `Message` are the only renderers, so the CLI and the REST handler cannot drift. `WriteText` takes a `printext.Styler`; pass nil for plain text. The style of a status word is mapped here, in `statusStyle`, because this package owns what `up` and `healthy` mean — `printext` only paints the meaning. `check_postgres.go` and `check_storage.go` hold the checks, `handler.go` the REST endpoint (200/503, standard `pkg/responder` envelope, uncacheable).
- `cmd/healthcheck.go` — the `health` command. It needs no running server: it opens the pool, runs the checker, prints the report, and exits 3 when unhealthy. `--json` prints the same object the REST handler publishes, `--short` one word, and `--timeout`/`--no-cache` tune the run. A database that cannot be reached is a result, not a command error. The Postgres target is rendered from the parsed DSN host/port/database, never the DSN itself, so a report cannot leak the password; the storage target is an absolute path.
- `api/connect/*.proto` — ConnectRPC contracts. `email/templates` — React Email sources compiled into `web/email`. `web` — SPA embed and static serving (debug/release variants).

Planned layout — the target shape of the scaffold packages:

- `internal/kernel` — module contract + registry (routes, middleware, start/stop). `internal/registry` — composition root wiring modules and shared dependencies.
- `internal/config` — koanf layering; `DefaultDataDir` (`storage`, relative to the working directory) is the single source for the `--data-dir` default and the storage health check. `internal/transport` — HTTP server, middleware, SPA serving. `internal/logger` — LogLayer setup. `internal/queue` — Postgres-backed in-process task queue. `internal/cache`, `internal/storage`, `internal/mailer`, `internal/jobs`, `internal/scheduler`, `internal/observer` — infrastructure surfaces.
- `modules/<area>/<feature>/` owns one feature: `schema.go`, `repository.go`, `service.go`, `handler_rpc.go` (plus `handler.go` when a REST surface exists), `module.go`. Business logic lives in `service.go`; handlers do transport mapping only. Follow this layout when implementing; do not invent a different file set.
- Persistence goes through `internal/datastore`; never open a second pool or a raw driver connection inside a module.
- Typed IDs come from `go.jetify.com/typeid`; the prefix is declared in the module's `schema.go`. Token and code rows use hashes plus DB `uuidv7()` instead of TypeIDs.
- Background work runs on `internal/queue`: register typed queues, enqueue typed tasks, keep the schema in migrations (`00008_create_queue_tables.sql`). Recurring maintenance belongs in `internal/jobs`.

## Conventions

- Config precedence, lowest to highest: built-in defaults → JSON config file → env file → system environment → CLI args. `--env-file` beats system environment; CLI args beat both.
- Config values support interpolation in the JSON source: `${NAME}` for plain substitution and `env:NAME` for environment-variable resolution. A missing referenced variable is an error, not an empty string.
- Every config key needs a default, a validation rule, and a line in `.env.example`. Add a test that keeps `.env.example` and `internal/config` in sync when the config package lands.
- Go 1.27 idioms: `encoding/json/v2` (with `omitzero`), `for range n`, `t.Context()` in tests, `errors.Join`, `slices`/`maps`, `min`/`max`, stdlib `uuid`.
- Shut down through context cancellation: servers, queue workers, and background jobs stop in order and drain in-flight work. New long-running components must implement stop.
- Comments are for what the code cannot say: an invariant, security rule, protocol requirement, or side effect. Write them short and functional. Never add a comment that only restates the code, narrates control flow, or repeats a name. Never leave phase/task/plan markers or signatures such as `phase *`, `Step N`, or `TODO(plan)`. Mark real future rework with a `TODO` or `FIXME` comment that says what to change and why.
- Do not add compatibility shims, fallback readers, or dual-write paths. Delete the obsolete path instead.
- Fix lint findings at the source. `//nolint` is not an accepted answer.
- Command output: pluralize counts through `printext.Plural` (never `%d migration(s)`), humanize durations through `printext.Duration`, indent per-item lines and leave outcome lines at column zero under a `status:` label so `grep '^status:'` works, and print a `database:` target line before touching anything. A command a script parses prints only its value (`migrate:version`). Colour and formatting come from `pkg/printext`, never from a command's own helper, and `--json` output is never coloured.

## Common Tasks

- Add a feature module: create `modules/<area>/<feature>/` with the standard file set, implement the `internal/kernel` module contract in `module.go`, and register it in `internal/registry`.
- Add an endpoint: write the proto in `api/connect/*.proto`, run `task rpc:generate`, implement the handler, then mount it in the registry.
- Add a migration: run `task db:create -- add_widgets` (or `go run -tags debug ./cmd migrate:create add_widgets`). It writes `database/migrations/<NNNNN>_<name>.sql` with the next free version and refuses a name another migration already uses. Fill in the Up/Down blocks, then run `task db:migrate`. The version must be `>= 1`, exactly 5 digits, consecutive with the previous file, and higher than the last; `migrate:create` maintains all four. A hand-written file must follow the same rules. Migrations are embedded in the binary, so a new file only runs after a rebuild — `go run` and the Taskfile rebuild on every call. Run `task db:validate` to check the files without a database.
- Add a seeder: add a factory file in `database/seeders/` that returns a `Seeder` and append it to `All()` in dependency order. Name it after the code, not the entity — `<Entity>Seeder` (e.g. `UserSeeder`) — because the report prints the name next to the record it created. Put the table constants and row structs in the owning `modules/<area>/<feature>/schema.go`, not in the seeder. Make `Apply` idempotent — guard every insert with `ON CONFLICT DO NOTHING` and report an existing record as skipped, because `migrate:seed` is expected to be safe to repeat. Never open a connection: `Apply` receives a `datastore.Querier` and the command owns the transaction.
- Add a dump object kind: add one writer to `dumpDDL`'s section list in `database/schema_dump.go` and place it where a restore needs it. Prefer the server's own deparse helper (`pg_get_*`, `format_type`) over assembling the definition in Go, and skip extension-owned objects through `pg_depend.deptype = 'e'`. Read the whole list before querying anything per item: a nested query on the same connection fails with `conn busy`. Add the case to the round-trip test in `database/backup_test.go` that applies a schema dump to an empty database — that is the check that catches a statement written in the wrong order.
- Add a test that touches the schema: get a database per test with `testutils.StartPostgres(t).NewDatabase(t)`. The shared container DSN points at one database for the whole test binary, so migrations applied by one test leak into the next. A test that needs two databases (a dump source and a target) may call `NewDatabase` twice; each call gets its own database.
- Add a config key: define it in `internal/config` with a default and validation, document it in `.env.example`, and honor the precedence order above.
- Add a background job: define a task type plus queue config in `internal/queue`, register the queue, and enqueue from the owning module.
- Local services: `docker compose up -d pgsql` for the database; the full stack (pgsql, redis, mailpit, silo, nginx) is in `compose.yaml`.
- The migration engine is goose v3 as a library. Every migration must define both `-- +goose Up` and `-- +goose Down`. goose requires one `Up`; the CLI's `migrate:down` requires the `Down`.

## Gotchas / Anti-patterns

- `codegen/` is gitignored build output. Never edit or commit it; regenerate with `task rpc:generate`.
- Migration numbering is sequential and 5 digits (`00009` is the highest today) and starts at `00001`. goose treats version 0 as the sentinel row and silently skips a file numbered below 1, so a `00000_*.sql` file never runs and never errors. Bump the version assertions in the migrator tests when adding one.
- `internal/queue/README.md` documents an API, a `module.go`, and migration `00010` that do not exist — the engine was removed and only the doc remains. Trust the code and `database/migrations/` over that file.
- Task targets live in `tasks/*.yml`, one file per group, and every one is included with `flatten: true` so a task keeps the name it had when the root file held it: `task db:migrate`, never `task database:db:migrate`. Flattening also keeps one flat namespace, so a task in one file can depend on a task in another by its plain name (`deps: [rpc:generate]`) — a prefixed include cannot see a flattened name. Add a new group by writing `tasks/<group>.yml` and adding a flattened include to the root `Taskfile.yml`; do not add a task to the root file. Root `vars` (`APP_NAME`, `APP_VERSION`, `IMAGE`) are inherited by every included file, so a split file needs no copy of them.
- The `compose:*` targets are the one exception and stay in the root `Taskfile.yml`, because they are the front door to the stack and the `compose.yaml` they drive lives there too. Do not move `compose.yaml` into `tasks/`; it must stay at the repository root.
- Keep `Taskfile.yml` targets aligned with the CLI (`key:generate`, `db:migrate` → `migrate:up`). A renamed command silently breaks the task.
- `task` (the default) runs `task --list` without `--sort none`: flattened includes have no declared order, so `--sort none` prints the groups in a different order on every run. Alphabetical order keeps each group together because every task carries its group as a name prefix.
- The root `--env-file` flag loads configuration for the server commands. A subcommand that writes a file must declare its own flag of that name; never treat the root flag as a write target, or `task run -- <cmd>` will rewrite `.env.local`.
- The README intentionally carries no architecture detail; the "Implemented today" list in this file and the code are the source of truth for what runs. When a scaffold package becomes real, update that list.
- Keep the README lean: setup steps, task table, certificates, deployment, license. Do not re-add architecture tables, emoji, or per-path inventories there.
- Integration tests without a Docker daemon must skip, not fail. Never widen a timeout to work around a hung container.
- Do not require valkey, S3, or SMTP for the default local path; Postgres plus local storage must be enough.
- Never rewrite a dotenv file the user owns without consent: print instead, or ask first. Destructive overwrite needs an explicit flag.
- Do not run destructive database commands (`migrate:reset`, volume removal) against a database holding state you did not create.
- A command whose action prints `not yet implemented` is not implemented. Never document, test, or rely on it as working, and never report a stub path as validated.

## Committing

- Stage explicit paths only; never `git add -A` / `git add .`. Verify with `git status` before committing.
- Message format: `{feat,fix,docs,refactor,chore}[(scope)]: <concise message>`.
- Never push. Commits are local unless the user asks for a push.
- Never commit on your own initiative — finish the work, recommend a message, and let the user commit. The exception is an explicit commit instruction in that turn.
- Always close a finished piece of work with a recommended commit title in chat, even when you did not commit. Use the format above, keep it one line, and list the changed paths under it.

Never run: `git reset --hard`, `git checkout .`, `git clean -fd`, `git stash`, `git commit --no-verify`, `git push --force`.
