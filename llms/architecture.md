# Architecture

Design notes for the implemented packages. `AGENTS.md` keeps the normative
rules; this file keeps the reasoning behind them, so a settled decision is not
re-litigated. Read the section for the package you are changing.

## database

### migrations/ (`database/migrations/`)

Goose SQL migrations, the single source of schema truth (8 files, `00001`–`00008`). Never embed DDL or create tables at runtime. Editing an applied migration does not re-run it — roll back with `migrate:down` and re-apply. `app_migration` also carries goose's `tstamp` (when a version was recorded), which `migrate:status` reads, so run times need no separate audit table.

### migrator.go

The engine over goose v3. `NewMigrator` loads the embedded migrations (`go:embed migrations/*.sql`) and builds a `goose.Provider` with a Postgres session locker and `app_migration` as the version table. Migrations run on the single-connection handle from `datastore.OpenMigrationDB`, never the pool. `Up`, `UpTo`, `Down`, `Status`, `Version`, `Pending`, `Applied`, `HighestVersion` return plain structs, so `cmd/` never imports goose. `Down(ctx, count)` rolls back one at a time so goose picks the next in the order it recorded; a version comparison cannot express out-of-order rollback. `MigratorOptions.Progress` receives a `ProgressEvent` per step. goose has no progress hook, so `database/progress.go` translates its verbose slog records (`executing statement` → `started`, `migration completed` → `applied`/`empty`/`rolled back`); only those two, so a goose rename costs the live per-migration line and nothing else, the caller's summary coming from the returned results. Without `Progress`, goose runs a nop logger.

### validate.go

`Validate` checks the embedded migrations without a database: unparsable file names (goose skips those silently), duplicate or non-consecutive versions, malformed annotations, unbalanced `StatementBegin`/`StatementEnd`, statements outside Up/Down, a file without a Down block. It does not parse SQL. `ValidateFS` runs the same checks over any `fs.FS` so tests use fixtures. `migrate:validate` wraps it and needs no DSN.

### create.go

`CreateMigration` writes a skeleton at the next version after the highest file on disk, and refuses a name already in use at any version, so the directory never holds two files describing the same change. Names are normalized (lowercase, non-alphanumerics collapsed to `_`), so `"Add Widgets"` and `add_widgets` collide. It creates files, never directories, and validates nothing about the SQL. `MigrationPrefixWidth` is the shared version padding.

### dump, backup, schema_dump, restore (`db:export` / `db:import`)

Design adopted from `JCoupalK/go-pgdump`, implemented here because that library hardcodes the `public` schema in ~25 queries and reads `information_schema.columns.data_type`, turning `citext` into a literal `citext` with no schema.

- `dump.go` holds the shared contract: the `public, internal, reference` schema list, `COPY` header prefix, `\.` terminator, `excludedTables` (`public.app_migration` is migrator bookkeeping, never dumped), `Connector`, `eachRow`.
- `backup.go` exports on one read-only transaction on one pooled connection, so every COPY sees one snapshot. Rows travel through `PgConn().CopyTo`, never `SELECT` + manual escaping, in `text` format not `csv`: text escapes the terminator, so a value of `\.` cannot end a block, while csv leaves it bare and truncates the table. Each table is ordered by its primary key, so the same state dumps to the same bytes.
- `schema_dump.go` renders DDL in restore order (schemas, extensions, enums, sequences, tables, constraints, indexes, functions, triggers, comments), one writer per kind, every definition from the server's own deparse helpers (`format_type`, `pg_get_constraintdef`, `pg_get_functiondef`, `pg_get_triggerdef`, `pg_indexes`), never re-derived; extension-owned objects are skipped via `pg_depend.deptype = 'e'`. Every statement is idempotent so a dump replays over an existing schema: `CREATE TABLE`/`INDEX`/`SEQUENCE`/`SCHEMA`/`EXTENSION` take `IF NOT EXISTS`, triggers become `CREATE OR REPLACE TRIGGER`, and `CREATE TYPE` / `ALTER TABLE ADD CONSTRAINT` — no such form exists — are wrapped by `guardedByTypeCheck` / `guardedByConstraintCheck` in a `DO` block that asks the catalog first; drop a guard and `TestSchemaDumpAppliesTwice` fails. Constraints must be ordered globally by type (all PK, then UNIQUE, then CHECK, then FK): per-table order puts `api_keys`' foreign key before `users`' primary key and Postgres rejects it. A catalog query must never run while another query's rows are still iterating on the same connection, or pgx reports `conn busy`; `dumpTables` reads the whole table list before any columns.
- `restore.go` reads every COPY block into memory, orders the blocks by foreign key (a dump is alphabetical, so a table can precede the table it references), then loads them. `--truncate` empties every table before any row loads, because `TRUNCATE ... CASCADE` would otherwise delete rows already restored. DDL in the file is ignored: the schema comes from `migrate:up`, so a dump cannot disagree with the migrations. A block that ends before its terminator fails rather than importing a partial table.

### compress.go

The `--compression` container and format detection behind `db:import`. `Compression` is `none|gzip|zlib|zip`, all from `klauspost/compress` — one dependency already in the module graph, so no format is hand-rolled. `pgzip` is deliberately unused: gzip-only, and its parallel writer splits the stream into independent blocks that cost ~7% of the ratio for a speed-up invisible beside the dump's own I/O. The dump is written plain first and compressed after it completes (`CompressFile`), so a failure during the dump cannot leave a half-written archive a reader would accept. A `*zip.Writer` owns its central directory, so `zipEntry` closes the archive, not the entry. Detection reads the file's own bytes (`detectCompression`), never its name: a renamed dump still loads and a name that lies is not believed. A recognized-but-unsupported container (`bzip2`, `zstd`, `xz`, `lzma`, `lz4`) is refused by name via `ErrUnsupportedCompression`; anything else is treated as plain SQL and held to the dump's own contract. zlib is told apart by a valid header (method nibble 8, first two bytes a multiple of 31). `InspectDump` counts blocks and rows for `--dry-run` without a database. **Never read the output buffer before closing the compressor** — the last block is only flushed by `Close`, and reading first yields a silently truncated file.

### seeders/

The default records a fresh database needs, behind `migrate:seed`. `Seeder` is `{Name, Apply(ctx, datastore.Querier, dryRun)}`; `Name` carries a `Seeder` suffix (e.g. `UserSeeder`, `UserSeederName`) because the report shows it beside the record it created, and a bare entity name would read as the record rather than the code writing it. `All()` returns them in dependency order; `Run` applies each over one querier and wraps a failure with the seeder name. The caller owns the transaction (`cmd/migrate_debug.go` passes `pool.WithTx`), so a failing seeder rolls back everything; the same `Run` works on the pool for a dry run. Every seeder is idempotent and reports the natural key of each record as created or skipped, so a second run is a no-op. `user_factory.go` creates the default account (`admin@example.com` / `@dmin123`, username `admin`, display name `Admin Sistem`, `is_admin`); the password is hashed with `pkg/crypto`'s scrypt hasher and is not computed on a dry run. Inserts use `github.com/huandu/go-sqlbuilder` (`Struct.For(sqlbuilder.PostgreSQL)`) guarded by `ON CONFLICT DO NOTHING`, so a conflict on any unique column keeps the existing row. `UserSchema`/`UserPasswordSchema` and their table constants live in the owning module, not here. `config_factory.go` and `jwks_factory.go` are still empty stubs.

### modules/identity/<feature>/schema.go

The table constants and row structs for that feature, so a table rename touches one line and a repository or seeder never hardcodes a name. `db` tags are the column names the query builder reads; structs list only the columns the application writes, so a migration can add a column with a default without touching Go code.

## cmd

### migrate_debug.go

Debug-only commands (`migrate:create|reset|seed|validate`). The actions live here rather than in `cmd/migration.go` because a release build would otherwise compile them into `unused`. `migrate:reset` rolls back everything and, with `--up`, re-applies in one run; on a database with nothing applied, `--up` alone applies the migrations, so `reset --up` also builds a schema from scratch. `migrate:create` takes a `--dir` flag defaulting to `database/migrations` and needs no database. `migrate:seed` first proves the schema is current by asking the migrator for pending migrations, so it refuses with the count and `run migrate:up first` rather than failing halfway on a missing column. A dry run needs no confirmation; a real run asks (unless `--force` or a non-terminal stdin) and runs in one transaction.

### migration.go

DSN resolution and the migration commands. The DSN comes from `envfile.DatabaseURL`, resolved from the root `--env-file` first and the process environment second; nothing else opens a connection. `migrate:up` and `migrate:down` ask for confirmation only when stdin is a real terminal (checked with `golang.org/x/term`, because `/dev/null` is also a character device) and proceed immediately when piped, so `task db:migrate` and CI never block. `up` takes `--to`, `down` takes `--count`; both take `--dry-run` and `--force`. `migrate:status` lists every embedded migration with the time it last ran and closes with the most recent run. `migrate:version` prints the bare version number for scripts and is the only command with no target header.

### database.go, database_cmd.go (`db:export` / `db:import`)

Export defaults to `storage/backup/tango-<YYYYMMDD_hhmm>.sql` (UTC) and creates that directory when missing, with or without `--overwrite`: a first run that happens to pass `--overwrite` has nothing to overwrite, so it must not fail for an unrelated reason. A `--output` path the user typed is used as-is and its directory is never created, so a typo stays visible. The generated name is readable to the minute, so a second export inside the same minute would land on the same path; `createExportFile` fails with `ErrDumpFileExists` instead of losing the first dump, and `--overwrite` is the consent. With `--compression` set the guard is on the **final** name (`.sql.gz`), not the plain intermediate, so a stale plain file cannot block a run whose compressed output does not exist yet, and the suffix is appended exactly once. `--force` is the shared confirmation bypass. Import takes the file as a required positional argument (`cli.StringArg{Required: true}`), not a flag, because a restore always has a source. A restore is destructive even without `--truncate` — it replaces rows in the tables the dump carries — so it always confirms unless `--force` is passed; `--dry-run` reports the work and opens no database at all. `printFields` renders a report as labelled values padded to one width, and `reportLabelWidth` pins that width so the target line (before the work) and the summary (after) share one column.

### helper.go

The shared rendering every command builds on, and the one place a spinner is created. One row shape for every migration report: `printMigrationRows` over `migrationRow` (version, state, time, name, duration), so all `migrate:*` reports read alike. `migrationLabel` shortens the row name — the version has its own column and `.sql` says nothing, so `00008_create_scheduler_tables.sql` prints as `create_scheduler_tables` — dropping the prefix only when it is really digits, so `add_widgets.sql` keeps its name; `last run` still names the full file, being a sentence not a row. `migrationStateWidth` sizes the state column from the words a report uses, so `applied` is not padded to a rollback's width while two lists from one command still share a column. `migrationRow.Measured` is separate from `Duration` because a measured zero is a real answer; `migrate:status` shows no duration, the recorded time being when a migration ran, not how long it took. Every outcome line carries a `status:` label at column zero (`printStatusLine`; `printSummary` for the timed closing line), so one `grep '^status:'` finds any command's result. `reportTarget` opens with `database: host:port/name` (never the DSN), so a run against the wrong server shows before it changes anything. A running migration is shown by the spinner, not a row: a row would be overwritten on a terminal and lost in a log. `newSpinner` returns nil off a terminal, so every spinner site is a nil check and a redirected run writes no carriage returns; stop it before the first result row, or its next frame lands at the start of that row. `reporter.restart` begins a second phase in place (`migrate:reset --up`) and must not be replaced by a new reporter: the migrator holds a method value from the reporter, so a new instance would never be called and the second phase would silently keep the first phase's column width and clock. Both halves of `migrate:reset` call it, including the fresh-database path; it lives in `cmd/migrate_debug.go` because `migrate:reset` is debug-only and a release build would otherwise flag it `unused`.

### healthcheck.go

The `health` command. It needs no running server: opens the pool, runs the checker, prints the report, exits 3 when unhealthy. `--json` prints the same object the REST handler publishes, `--short` one word, `--timeout`/`--no-cache` tune the run. A database that cannot be reached is a result, not a command error. The database target is rendered from the parsed DSN host/port/database, never the DSN itself, so a report cannot leak the password; the storage check names no path on the endpoint, while the CLI report (`StorageCheckWithTarget`) shows the resolved directory, because an operator reading the terminal owns the machine.

### logger.go

How the process logger reaches a command. `initConfig` installs a `loggerState` on the context and the root `After` closes it, so a run flushes what it queued. The logger itself is built **lazily** (`loggerFrom`), not in `Before`: `config:generate` and `key:generate` run before a usable configuration exists, so building eagerly would break the two commands that bootstrap a fresh checkout. The state holds the configuration and a `sync.Once`, so the first command that logs builds one logger and every later call gets the same one. `loggerFrom` reports the failure rather than swallowing it — a command that asked for a logger and did not get one must say so, because the alternative is a run that looks healthy and writes nowhere. `observerState`/`observerFrom`/`closeObserver` live in the same file and work the same way for traces and metrics, because the two have the same lifecycle and the same reason to be lazy; they are separate state so a command that logs does not build a tracer. The root `After` closes the **observer first**, then the logger: a signal drained by the observer may be reported through the logger, and a logger closed first would drop that line. `closeObserver` **reports** a failed drain and returns nil — telemetry is a side channel, so a collector that is down at shutdown means some spans were lost, which is worth saying and is not a reason for a command to exit non-zero. The two shutdown timeouts are separate constants because the metric reader needs longer than a log batch to drain.

### loggersmoke.go

`logger:smoke`. It emits one line per level through every configured transport and prints where each one writes plus the LogsQL query that reads the line back, so the logging path can be proved end to end against a real backend before anything depends on it. It builds the logger itself rather than calling `loggerFrom`, because the command that exists to diagnose logging should not fail before it can say which transport broke. The probe field is named `probe`, not `level`: `level` is the structured transport's own key, and a field of that name would put the same key in the JSON object twice.

### otelsmoke.go

`otel:smoke`. It records one span and one measurement through the providers the configuration enables, and prints what each signal is doing, so tracing and metrics can be proved end to end the way `logger:smoke` proves logging. It goes through `observerFrom`, the same accessor a real command uses, so the run proves the wiring rather than a pipeline assembled for the test. The counts in the closing status line are captured **before** the drain: `Shutdown` releases the providers, so checking afterwards would read every signal as off and report a run that proved nothing as if it had proved something.

## pkg

### printext

How output is rendered for a human, shared by the CLI and `internal/health`. It owns colour and formatting. A `Style` names what text means (`StyleOK`, `StyleFail`, `StyleWarn`, `StyleLabel`, `StyleMuted`); a `Palette` decides the colour, so a renderer marks meaning without knowing a colour. `Style` is the vocabulary, `Colour` the four values a palette paints. Formatting: `Duration` (three decimals through `humanize.SIWithDigits`), `Plural`, `PadRight`. Colour is decided per destination, not per process: fatih/color reads `os.Stdout` once at start-up, which is wrong for a writer that is a buffer in a test or a file in a redirected run, so `NewPalette` asks `IsTerminal` and honours `NO_COLOR`. A buffer is never a terminal, so a test sees plain rendering without asking. Pad before colouring, never after: an escape code is invisible but not zero-width to `fmt`, so padding a painted string breaks its column. The package never decides layout — column widths, labels, and which lines a report holds belong to the caller.

### crypto

`Cipher` seals recoverable values with AES-256-GCM and the exact `enc:` prefix; `PasswordHasher` produces PHC strings (scrypt default, Argon2id opt-in). Keys are 32 bytes stored as 64 hex characters (`GenerateKeyHex`, `ParseKeyHex`, `NewCipherFromHex`). `KeyGenerator` always emits all four variables: `APP_SECRET_KEY`, `AUTH_PRIVATE_KEY`/`AUTH_PUBLIC_KEY` as base64 (raw, unpadded) JWK JSON with `alg` and a thumbprint `kid`, and `AUTH_SECRET_KEY`. The key pair and the HMAC secret are independent: defaults `ES256` and `HS256`, and a passed algorithm replaces only the role it can fill (asymmetric → key pair, `HS*` → secret). Passwords are hashed, never encrypted. Do not add another encryption or hashing format.

### envfile

Dotenv reader/writer that preserves comments, blank lines, and key order; new files are written `0600`. Owns the `DatabaseURL` key constant (`DATABASE_URL`); pkg/ cannot import internal/, so the config layer derives the same name through `EnvName` and a test asserts the two agree. `key:generate` declares its own `--env-file` flag (the root flag only loads config) and owns the I/O: it only prints unless that flag is given, creates a missing file, and asks before replacing the values of an existing one (`--overwrite` skips the prompt).

### responder, validate, jwtutils, testutils

`pkg/responder` — the API envelope, pagination, request IDs (documented in `docs/api-response.md`). `pkg/validate` — request decoding and ozzo v4 code-first validation. Handlers use these; no hand-built envelopes or ad-hoc field guards. `pkg/jwtutils` — JWT signing/verification with typed private claims. `pkg/testutils` — shared testcontainers Postgres, Mailpit, MinIO.

## internal

### datastore

The Postgres adapter. `NewPostgres` owns the single `pgxpool` of the process (sane pool defaults, connect-time ping, `Ping`/`Stats`/`Close`), `Querier` is the shared pool/transaction surface, and `WithTx` commits when the callback returns nil and rolls back otherwise (including on panic); the callback receives the `Querier`, so a transaction passes to any repository, seeder, or store written against it. Every pooled connection sets `search_path` and `timezone` through `RuntimeParams`, so a recycled connection keeps the same session defaults. `Acquire` hands out a connection for work that must stay on one backend (LISTEN, session advisory locks); callers must release it. ErrNoRows is re-exported so repositories do not import pgx. Migrations never use the pool: `OpenMigrationDB` / `(*Postgres).MigrationDB` return a `database/sql` handle pinned to one connection, because goose holds a session advisory lock and needs every statement of a run on the same backend.

`datastore.Valkey` is the key-value backend (`internal/datastore/valkey.go`), on `valkey-io/valkey-go`: `NewValkey(ctx, ValkeyOptions{URL, DB, ApplicationName})` parses the URL with `valkey.ParseURL` (the grammar `isKVURL` mirrors), lets an `opts.DB` of zero or more outrank the index the URL carries, names the connection after the application, and verifies connectivity with a ping before returning — an unreachable backend fails the startup, and a failed construction hands out no client. The ping error carries no target: `RedactKVURL` is the one rendering, applied by the caller. The driver is opt-in: `kvstore.enable` decides availability, and nothing dials the backend while no feature selects it.

### cache

The key-value cache drivers, behind one `Cache` contract (`Get(ctx, dst, key)` appends into the caller's buffer — an API designed to be used in zero-allocation mode — plus `Set` and `Del`, each carrying the caller's context, which the remote driver owns a round trip for). `New(cfg, kv)` is the entry point a composition root calls, and Noop is the driver it hands out whenever caching does not run: the cache switched off (`cache.enable` defaults to false — a feature that has not decided to be cacheable cannot grow one by accident), the kvstore driver named while `kvstore.enable` is false (a cache that cannot reach its server is a run without caching, not a broken system — which is why the cache alone among the kvstore features is exempt from `kvStoreDrivers`), or an unknown driver. Noop answers every read with a miss, so a feature never branches on the caching question.

`cache_memory.go` is the in-process driver, adopted from `VictoriaMetrics/fastcache` without the dependency: entries are appended into 64 KiB byte chunks (nothing for the GC to scan inside a chunk), an index of `map[uint64]entry` hashes each key with the seeded stdlib `hash/maphash` (per-process seed, so no hash can be crafted offline; `cespare/xxhash` was left unused for this reason), the whole ring is cleaned when the `cache.max_memory` budget is spent while keeping the chunks it grew, and an entry carries its own TTL (`cache.ttl` is the default) measured on the monotonic clock — `cacheEpoch` is the process-start baseline, expiry deadlines are offsets from it, and `monotonicNow` reads them, so a wall-clock step can neither age an entry early nor resurrect an expired one. Collisions are handled where bigcache overwrites: every entry stores its key, a lookup verifies the bytes before answering, and a colliding entry takes a secondary slot — two keys sharing a hash keep working, only a third evicts the secondary. `Reset` is the only drain the driver takes — the budget, the TTLs, and the ring's own reset already bound what a running cache holds, so there is no flush goroutine to stop. The batch methods (`GetMany`/`SetMany`/`DelMany`) exist for the remote driver's sake — one round trip instead of one per key — and are a loop over the single-key calls here, since an in-process read has no round trip to amortize; only the batch's returned map allocates, a single hot `Get` into a roomy `dst` still allocates nothing, which `cache_memory_bench_test.go` pins.

`cache_valkey.go` drives the shared `datastore.Valkey` client: keys are namespaced under `ValkeyKeyPrefix` (`tango:cache:`) — features sharing one server are isolated by prefix, not by logical database index, which Valkey cluster does not support; the backend's memory is the server's business (`maxmemory`, `maxmemory-policy`, per-key TTL) — and any backend failure reads as a miss, because a cache may degrade and the feature behind it may not. The batch methods are where the contract earns its keep here: `GetMany` is one MGET, `SetMany` one pipeline of SETs through `DoMulti`, and `DelMany` one DEL naming every key — each a single round trip, with a nil reply element or a backend error reading as a plain miss.

### health

The health check engine, adopted in design from `alexliesenfeld/health` but implemented here (no dependency). `NewChecker` takes named checks, runs the due ones concurrently under a global timeout, caches each result for a TTL, recovers a panic into a failure, and aggregates. Two vocabularies on purpose: a component is `up`/`down` (`Status`), the system is `healthy`/`unhealthy` (`GlobalStatus`). `Check.Optional` is reported but excluded from the aggregate, so an optional backend is never an outage; `Check.Target` names what was inspected and appears in the text report. Metadata comes from `WithInfo` (static, such as the build version) and `WithInfoFunc` (computed per call, such as `Uptime`); a static key outranks a computed one. The JSON form is explicit (`marshal.go`) and byte-identical for the same state: durations in milliseconds under `took_ms`, details as an ordered array, and the info entries flattened to the top level in sorted key order (never nested under `info`), because `encoding/json/v2` does not sort map keys; an info key that shadows a wire field (`status`, `details`, `took_ms`) is refused at construction. `Result.Duration` is the length of one check run, not uptime. `WriteText`, `WriteShort`, `Message` are the only renderers, so the CLI and the REST handler cannot drift; `WriteText` takes a `printext.Styler`, pass nil for plain text. The style of a status word is mapped here, in `statusStyle`, because this package owns what `up` and `healthy` mean — `printext` only paints the meaning.

Checks (check names are generic — `database`, `kvstore`, `storage` — never the product behind them, so a published report does not advertise the engine a deployment runs):

- `check_database.go` (`DatabaseCheck`) — pings the pool, so it also fails while the pool is exhausted.
- `check_kvstore.go` (`KVStoreCheck`) — pings the shared key-value backend; wired in only while `kvstore.enable` is on, since a disabled backend is never dialled and reporting it down would describe a dependency the application does not have.
- `check_storage.go` (`StorageCheck` / `StorageCheckWithTarget`) — probes the data directory: missing, not a directory, not writable (real write-and-remove probe, mode bits alone are not enough), or world-writable (a failure, because it holds uploads and certificates). The endpoint publishes the plain check; `StorageCheckWithTarget` reports the resolved absolute path and is for the CLI report, which an operator who owns the machine reads. Error messages name the problem, never the path.
- `handler.go` — the REST endpoint (200/503, standard `pkg/responder` envelope, uncacheable).

### observability stack (docker)

`docker/compose-metrics.yaml` — the observability stack (OpenTelemetry collector, VictoriaMetrics, VictoriaLogs, VictoriaTraces, Perses), included by `docker/compose.yaml`. **The collector is what makes one `otel.endpoint` work**: each Victoria service serves OTLP on its own port, and `docker/otelcol.yaml` fans the three signals out to them, so the application names one address and the routing lives in the collector rather than in the configuration. The paths are the backends' own, not the protocol's: VictoriaLogs serves OTLP on `/insert/opentelemetry/v1/logs` and VictoriaTraces on `/insert/opentelemetry/v1/traces` — **not** `/v1/logs` and `/v1/traces` — and VictoriaMetrics ingests metrics on `/opentelemetry/v1/metrics`. The application ships to the collector's protocol paths and the collector rewrites them, which is why the app config names no path at all. Perses is provisioned from `docker/perses/*.yaml` through the `provisioning.folders` entry in the inline config; those resources are `GlobalDatasource`, not project-scoped `Datasource`, because the config switches project datasources off and this stack has no projects — a project-scoped file is provisioned into nothing and logs `project "default" doesn't exist`. The scrape job for the application points at `host.docker.internal:3080` with `metrics_path: /metrics`; `serve` serves that path once it runs, and the job reports `down` only while `serve` itself is not running.

**VictoriaLogs (v1.52) and VictoriaTraces (v0.11) moved their base image from Alpine to distroless**, so neither carries a shell or an HTTP client: an exec healthcheck cannot run at all (`exec: "nc": executable file not found in $PATH`), Docker marks the service unhealthy, and every `depends_on: service_healthy` behind it never starts — Perses stays in `Created` and the stack looks broken while both services are serving. Neither has a flag that probes its own endpoint (`-health` is VictoriaMetrics/VictoriaLogs#1565, still an open pull request, #1741), so the two distroless services carry **no** healthcheck and the services waiting on them wait for `service_started`; the check that matters runs from the host, where curl exists. `metrics:up` ends with `metrics:health`, which probes each endpoint and retries until it answers, bounded by `TIMEOUT` (60s) so a service that never comes up fails the run. Perses answers on `/api/v1/health`, not `/health`. When `-health` ships, reinstate the healthchecks and the `service_healthy` conditions. VictoriaMetrics is still Alpine-based and keeps its own healthcheck.

### tasks/metrics.yml

`metrics:up|down|health|endpoints|query|traces|targets|smoke|smoke:otel`, the shortcuts for the stack. `metrics:query` takes a LogsQL query after `--`, `metrics:smoke` runs the logging smoke command with `.env.local`, and `metrics:smoke:otel` runs the trace and metric one. The compose targets stay in the root `Taskfile.yml` next to the compose file they drive; this group only drives the tasks a developer runs while wiring the application to the stack. A Task variable holding a space is quoted into one word, so a loop over several values is written as plain shell inside one `cmd`, not as a Task `for`.

### pkg/testutils/victorialogs.go

`StartVictoriaLogs`, the log store container for integration tests, with `Query` and `AwaitQuery` (LogsQL over the query API). One container is shared per test binary, so a test looks for its own marker rather than for an empty store. The wait is an HTTP request on `/health`, not a port check: the port listens before the store can ingest, and a test that shipped to a half-started store would fail on a line that was never written. Shipping is batched, so `AwaitQuery` polls rather than sleeping a fixed time.

### logger

The logging stack. One LogLayer core sits behind a `*slog.Logger` (`integrations/sloghandler`), so application code and every dependency that logs through `log/slog` emit into the same pipeline; feature code calls `slog`, never LogLayer. `New(cfg, opts...)` walks `log.transport` in order and builds each named sink: `console`, `file`, `otlp`. The list is what switches a sink on, so there is no second flag that could disagree with it; a name no sink matches fails construction rather than being skipped, and `Validate` refuses an unknown name, a repeated name, and an empty list. The console is the only sink with a rendering choice, carried by its own key `log.console.format` — `pretty` (the `pretty` transport) or `structured` — because what a person reads in a terminal and what a machine reads from a log file are different questions; a file or a collector keeps JSON regardless, has no key to choose, and `Validate` reads the format only when the console is named, so asking for a colourised console cannot put escape codes in the file. Colour is decided per destination (`isTerminal`, the same rule `pkg/printext` applies), so a redirected run and a test buffer stay plain. The threshold lives on the logger (`levelFor`), not on a sink, so every destination agrees on what is worth emitting. `FlattenMetadata` is on, so fields and per-call metadata merge at the root and an entry reads the way slog's own JSON handler writes it. `New` fails rather than degrading — a deployment that asked for a file or a collector and silently got neither has lost the logs it is being trusted with — and `release` closes whatever was built before a later sink failed. `Shutdown` drains the collector first (its batch processor holds queued records nothing else can flush), then releases the file descriptor, and is idempotent. The file sink's path is derived, not configured: `LogFilePath` is `storage.local_path` + `/logs` + `tango.log`, so the process has one data directory and no second path that could disagree with it.

The OTLP sink passes **every** exporter option explicitly, including a nil `WithTLSClientConfig` on a plain http endpoint: the exporter otherwise reads `OTEL_EXPORTER_OTLP_*` for its endpoint, headers, compression, and TLS material, which would be a second configuration source deciding what a deployment logs and where, and the resource is built with `resource.NewSchemaless` rather than `resource.Default` so `OTEL_SERVICE_NAME`/`OTEL_RESOURCE_ATTRIBUTES` cannot attribute a record to a service the shell named. The gRPC branch closes the same door with explicit transport credentials rather than `WithInsecure`, because credentials take priority over the insecure and the TLS defaults alike — see `internal/observer` for the full reasoning, which the two packages share. The address is `otel.endpoint` and the resource is built from `otel.service_name`/`otel.environment`, so a record, a span, and a measurement of one service carry the same identity into the same collector.

Every entry carries the calling function, file, and line **only at debug level** (`sourceGate`): slog always captures `Record.PC` and the handler forwards it, so the gate at the frontend zeroes it for every level above debug — the call site tells a reader where the code lives, which is a debug-only fact, and one wrapper covers every sink (console, file, echo, OTLP) instead of a policy each transport remembers.

**`Slog()` is the frontend and the only way feature code writes a line**; the LogLayer core is not exposed — its API is a second way to say what slog says, and using it would split the codebase into two logging idioms, the second of which skips the handler the rest of the stack is wired through. `With(...)` and `WithGroup(...)` are slog's own and work here, because the handler behind the logger implements them: a field added through `With` reaches every later record and a group nests what follows, which is the idiom for request-scoped fields (asserted in `TestSlogChainCarriesFieldsThroughThePipeline`). **Call the `*Context` methods wherever a context is in hand** (`InfoContext`, `WarnContext`, ...): the otellog sink correlates the record with the span the context carries (asserted in `TestSlogContextCorrelatesLogsWithTheActiveSpan`), and a plain `Info` writes a record with no trace ID — logging without the context is what kills log↔trace correlation. **Errors are logged as rendered text under `err`** (`"err", err.Error()`): the error slot LogLayer's serializer renders is reachable only through LogLayer's own API, which feature code does not hold — the official slog integration maps every attribute onto fields, and a raw error value there encodes as an empty object (asserted in `TestErrorsAreLoggedAsRenderedText`).

**The console and file sinks are async, zero-drop** (`internal/logger/async.go`): each sink is one worker owning a bounded queue (8192) that **blocks** its producers when full — a burst costs the response path one enqueue, never a write syscall, and overload turns into latency, never into a lost line. The console renders into a batch buffer flushed on every drain, so a burst costs one syscall instead of one per line. `Close` (which LogLayer calls to pre-flush before a `Fatal` exit, and `Shutdown` calls at the end of a run) drains the queue before releasing the inner transport, so a graceful stop and every queued entry before it are written; only a `kill -9` between enqueue and drain can lose what the queue still holds. A send that races with the close is written synchronously rather than dropped. `Logger.Flush` drains without stopping the sinks — what a test that reads its buffer after a log call uses. The OTLP sink is deliberately not wrapped: its batch processor already queues in the background.

**A run whose transports do not name the console is not blind**: `echoSink` carries warnings and errors to stderr — deliberately unconfigurable, deliberately unqueued — so an operator watching the service still hears when something is wrong, without a second copy of every routine entry; the startup and shutdown milestones for that same deployment are the two lines `serve` writes to stderr directly.

### observer

Traces and metrics, the two signals `internal/logger` does not own. It follows the logger's shape: the resolved configuration is the only source of truth, each signal is opt-in, and a signal nothing enabled dials nothing. It also owns `exporter.go`, the OTLP exporter plumbing (gRPC credentials, TLS, compression, signal routes) all five exporters of the process share — the logger's log sink imports it rather than carrying a copy, so a decision about what an exporter may read from the environment is made once. `New(ctx, cfg)` returns an `Observer` with every signal off when neither `otel.tracing.enable` nor `otel.metrics.enable` is set, so a caller never checks for nil before `Shutdown`.

**Nothing on the request path blocks**: spans go through a batch span processor and measurements through a periodic reader, so recording enqueues and returns, and a collector that is slow, unreachable, or absent costs dropped telemetry rather than a slow request — the queue is bounded by `otel.queue.max_size` and drops the oldest item when full. Metrics leave by **two routes at once**, deliberately: the periodic reader pushes to the collector, and the Prometheus bridge serves the exposition at `otel.metrics.prometheus_path` on the application's own port, which is what the `tango` scrape job in the compose stack reads. `MetricsHandler` exposes the handler for that path; **`internal/transport` mounts it at `otel.metrics.prometheus_path`** on the router it builds, so the compose scrape job reports the service once `serve` runs — a disabled signal mounts nothing, which is why the endpoint is absent rather than empty. The bridge writes into a registry this package owns (`newRegistry`), not the Prometheus default: otherwise a scrape would attribute a dependency's metrics to this service and the Go runtime's collectors would appear on every endpoint. `Observer.Shutdown` stops the metric provider before the tracer provider, and `MetricsHandler` returns nil for a disabled signal rather than exposing an endpoint that reports nothing. `SetGlobals` installs only the enabled providers, so a switched-off signal keeps the SDK's no-op global.

The two protocols are separate exporter packages with separate option types, so the exporter is chosen in a branch per signal and there is no shared option list; the branch for a JSON protocol exists only on the trace path, which is the only one the SDK can encode. Like the logger, **every exporter option and every resource attribute is passed explicitly**: the SDK otherwise reads `OTEL_EXPORTER_OTLP_*`, `OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`, and `OTEL_SDK_DISABLED`, which would be a second configuration source deciding what this process reports and where. The gRPC exporters read those variables too — `ApplyGRPCEnvConfigs` runs before a caller's options, so a passed option wins — and TLS material is closed the same way at both ends: `grpcTransport` passes explicit credentials rather than `WithInsecure`, because credentials take priority over the insecure and the TLS default alike, and the HTTP path passes a nil `tls.Config` to stop the certificate options from being loaded. `samplerFor` maps `otel.tracing.sampler` onto the SDK samplers, including `parent_ratio` (`ParentBased(TraceIDRatioBased)`), so a service that receives an already-sampled request keeps the trace whole. A route is applied only when the configuration names one or the endpoint carries none: an address that already names a route says where the signal goes, and overriding it with the default would send it elsewhere. The `otel/log` module is pinned at v0.19.0 (see the decision records below); the trace and metric exporters are on the core version line and stay free.

### queue

The embedded task queue, ported from `mikestefanello/backlite` (MIT, SQLite) and owned here: the schema comes from migration `00008_create_scheduler_tables.sql` (the queue and the scheduler state share it), the queries from `go-sqlbuilder` (the seeders' idiom), and the logs from the process `*slog.Logger` the caller passes — the package never builds its own. A `Task` is a payload type whose `Config()` names its queue; `NewQueue[T]` pairs that type with a decoded processor, and `Client.Add(...).Save()` inserts it with a Go-generated UUIDv7, so a caller can reference the task before any commit — `Add` is variadic, which is the batch API: one statement, one transaction.

The dispatcher claims with one `UPDATE ... RETURNING` over a `FOR UPDATE SKIP LOCKED` subquery — never claimed, or claimed before `queue.release_after`, and past its `wait_until`, ordered by `priority DESC` then insertion order, so a higher priority is claimed first — so two processes sharing the database never run one task twice, and a lost worker's task is reclaimed. `TaskAddOp.Priority` ranks a task at enqueue time, negative refused; `Client.Cancel` removes a task that has not been claimed yet and reports `false` for one in flight, which finishes its lifecycle. The engine is event-driven: a save notifies it, a delayed task arms the fetcher's ticker, and when nothing is claimable the ticker falls back to one minute — the one bounded poll, which is what makes reclaim independent of traffic.

Outcomes: success deletes the task (archiving it in one transaction when the queue's `Retention` asks), a retryable failure releases it for its `Backoff`, an exhausted one archives with the error — the dead letter — and a processor panic is a failure, not a crash; `Dead` counts a queue's dead tasks and `ReplayDead` re-enqueues the ones that kept their payload under a fresh identity, so the archive is a replayable dead letter queue, not a graveyard. When `queue.encrypt` is set the client seals every payload at rest with `pkg/crypto`'s `Cipher` (the `enc:` prefix marks a sealed payload) and opens a claimed payload before the queue decodes it — an in-flight plaintext task from before the flag flipped still runs, and the archive keeps the sealed form so a replay rides the same path. A task whose queue was never registered is re-queued on its own clock and logged — it may be waiting for a deploy — and spends no attempt. `WithTx` callbacks receive the shared `Querier`, so `TaskAddOp.Executor` joins the caller's transaction, and the caller owes it a `Notify()` after the commit.

### jobs

The concrete jobs the application runs on the queue: one job per `*_job.go` (task type, `QueueConfig`, processor), with `Register` the one place the queue list is spelled out and the recurring ones seeded, and `Scheduled` the list the cron scheduler enqueues — empty until a feature asks for a cron schedule, because a recurring job that runs on a fixed interval belongs with `Register`, whose self-enqueued successor is durable without a second mechanism. A recurring job keeps its own schedule: its processor enqueues the next instance before returning, and `Register` seeds one only while none is pending, so a restart never multiplies the schedule. `cleanup_job.go` is the first: it purges the completed records their retention has expired, on `queue.cleanup_interval`. The engine's own goroutines know none of the jobs — jobs are application code, the queue is infrastructure.

### scheduler

The durable cron scheduler: robfig/cron v3 (zero dependencies) owns the timing, Postgres owns the claim, and the queue owns the execution — a claimed tick only enqueues a task, never runs logic. The state lives in `scheduler_jobs` (migration `00008_create_scheduler_tables.sql`, shared with the queue), one row per job: `next_due` is the claim cursor. Every replica fires the cron time; `fire` opens one transaction that locks the row `FOR UPDATE`, reads the database's own `now()` (so replica clock skew cannot double-fire), advances `next_due` from the old due — a cron spec resumes at its next mark instead of bursting, an `@every` spec catches up one slot per tick — and enqueues the task through `TaskAddOp.Executor` in the same transaction, so a tick is enqueued exactly once and never lost between claim and insert; `Notify` comes after the commit. A failed tick leaves the row untouched and retries at the next firing; the row lock replaces leader election (no elector, no leader lifecycle), and seeding is `ON CONFLICT DO NOTHING`, so a row a deploy created keeps its schedule in motion. `New` refuses a missing store or client, an empty or duplicated name, a nil task, and a spec that does not parse; `scheduler.timezone` resolves a spec that names no zone (robfig's `WithLocation` sets the run loop's clock but not the parser's, so the `TZ=` prefix is prepended and the spec is parsed once).

### storage

The file storage engine and its two backends — the local filesystem under `storage.local_path` and an S3-compatible store (`storage.driver` selects; `New` builds only the selected one, so a local deployment never opens an object-store client). A file is never stored whole: the `Chunker` cuts it into `storage.chunk_size`-byte chunks, hashes each with SHA-256, and the hash is the chunk's address in the backend (`ChunkName`'s `chunks/<2 hex>/<hash>` layout is the contract both drivers and the garbage collection share). Content addressing buys three things at once — dedupe (two files sharing a chunk share one object), change detection (a manifest diff names exactly the chunks that moved), and idempotence (a retried upload rewrites the same bytes under the same hash). The manifest — one `storage_files` row plus its `storage_chunks` rows (migration `00009`) — lives in Postgres, the durable place a diff reads from; the root hash over the chunk hashes is the one-value fast path that says a sync has nothing to upload.

Keys are the feature's naming, made safe at the door: `Key(parts...)` composes a multi-purpose key (`avatar/usr_1/128.png`, `user-files/…`) by mapping each part onto one path segment, `ValidateKey` refuses any key with a traversal, absolute, or hidden segment, and every manager entry point validates before it builds a path — a key cannot walk out of the staging directory. Metadata is the feature's free-form record (content type, original file name, owner) in a JSONB column: written at `Stage` time, rewritten by `UpdateMetadata`, carried but never interpreted by the engine.

The request path is a local disk write and nothing else: `Manager.Stage` writes the file into `storage.local_path/staging` through a temp file and a rename (the watcher never sees a half-written name) and commits the intent row — metadata plus the staging fingerprint — before the upload is enqueued. Everything else happens on the durable queue. `storage_upload` (`ChunkUploadTask`, enqueued by the watcher when a staging path settles, or by any caller) runs `Manager.Sync`: a pending manifest whose staging fingerprint (size + mtime) matches the staging file is **reused whole** — the checkpoint that keeps a retry from re-hashing a large file — otherwise the pass streams the file for hashes only (memory stays at one read buffer whatever the file's size; a file of 16 MiB or more is hashed in parallel instead — each worker reads its chunk at its own offset, the same shape as the upload pass, and memory stays at workers × chunk size). The chunk list is checkpointed before the first chunk travels; the diff against the backend comes from one batched probe per two-hex prefix (a handful of LISTs, never one HEAD per chunk); the uploads run in parallel through an errgroup bounded to four workers, each borrowing one chunk buffer from a pool and re-reading only its chunk's byte range via `ReadAt` — a sync costs workers × chunk size of memory, never the file size. The ready manifest commits in one transaction, and the staging copy is removed only if its fingerprint still matches what the sync read — a file re-staged underneath a running sync is left for its own round, not destroyed.

The watcher (`fsnotify`, the one new dependency beside the AWS SDK) watches every directory under staging — nested keys are first-class — debounces per path (one timer per key, reset by every write, so a burst of writes is one settle), and scans the tree at start, so an upload that outlived its process is picked up by the next run; it is a serve-run component stopped through context cancellation. Deletion keeps any chunk another file still references, and `storage_gc` (a recurring job on the cleanup pattern, re-enqueuing its own successor at `DefaultStorageGCInterval`) sweeps the backend against `ReferencedHashes` — the drain of the paths a crash can leave. `Manager.Open` reads a file back as one stream that fetches chunks on demand; no whole-file buffer exists on the read path either. The S3 driver holds the one AWS client of its own (static credentials from `storage.s3.*`, path style for MinIO/Silo) and translates the protocol's not-found shape into `ErrNotFound` at its edge.

The upload round has two feature extension points, both nil by default and wired in the registry (`WithBeforeSync` / `WithAfterSync`). `BeforeSyncHook` is the gate: it runs before the staging file's fingerprint is read, so a hook that rewrites the file (sanitize, re-encode) is hashed from its own output, and an error refuses the file — the queue retries, and a hook that keeps refusing walks it to the dead letters. `AfterSyncHook` is the post-processing point: it runs once the manifest is ready and every chunk is durable, before the staging copy is removed — thumbnails, metadata enrichment, notifications (this, not polling, is the intended answer to the TODO below). Both run on the queue's retry path, so **idempotence is their contract**: a retry replays them (a failed after-hook leaves the staging file, and the retry reaches the hook through the finished-manifest fast path without re-hashing). A hook must also stay quick — long work belongs in a job the hook enqueues, not in the upload worker's slot.

When it does, a handler maps `Progress` onto either a polling response (simplest, one GET per key) or a ConnectRPC server-streaming channel (push updates; needs stream lifecycle and a poll interval behind it). ## Planned layout

The target shape of the scaffold packages.

### internal/config (planned)

The configuration layer, on koanf. The JSON config file is the single source of truth: `Load` merges three layers in fixed precedence — built-in defaults, the config file, then the command-line flags. Merge is last-wins per key, not per section, so a source that sets one leaf leaves its siblings alone. **The environment is deliberately not a layer.** A variable reaches a config key only where the file references it, with `env:NAME` as a whole value or `${NAME}` inline, so a user names variables whatever they like, the file decides which key each fills, and a stray export in a shell can never change a value nobody referenced. A directive naming a missing variable is **deferred**, not a load failure: the key keeps its default, `Config.Unresolved` records the variable, and `Validate` reports it only where the missing value leaves the key unusable — so `migrate:status`, which reads only `database.url`, is never blocked by an unset JWT key, and an unset `APP_MODE` falls back to development without an error. The file is **required**: a missing one is `ErrNoConfigFile`, not a fallback to the defaults, so `config:generate` is the first command a fresh checkout runs. `Load` resolves but does not validate, so a command that needs one key is not blocked by a key it never reads; `cmd/config.go` exposes `configFrom(ctx)` for that case and `fullConfigFrom(ctx)` for a command that needs the whole configuration. A duration key is written as a plain number of seconds (`"access_ttl": 900`), never as a duration string: koanf hands a JSON number to mapstructure as a `float64`, which would set a `time.Duration`'s nanoseconds, so `900` would silently mean `900ns`. `internal/config/duration.go` holds `durationKeys`, the list of keys read as seconds; `normalizeDurations` converts a numeric value on those keys only, before each layer is merged. A duration string (`"15m"`) is still accepted, so a hook on the Go type is wrong: a duration is an `int64` and so is an ordinary number. A test asserts `durationKeys` is exactly the set of `time.Duration` fields on `Config`. `app.mode` (not `app.env`) names the runtime mode. The struct is the schema: a field with a koanf and json tag, a default in `Default`, and a rule in `Validate` makes a key work in every source at once. Keys are dotted (`database.max_conns`); `EnvName` is the *convention* the generated file and `.env.example` spell a key as (`DATABASE_URL`), not a loader mapping — deriving it would turn `AUTH_SECRET_KEY` into `auth.secret.key`. A file key that names no config key is dropped, so a stray entry cannot replace a section with a scalar and break the decode.

`Sample()` renders the starter file: every key with its default, every key in `secretKeys` as an `env:` directive rather than a literal, and every key in `envKeys` (`app.mode`, `app.base_url`, `app.assets_url`, the `otel.*` deployment keys, the five `mailer.smtp_*` keys, the `kvstore` and `storage.s3` deployment keys) as a directive naming the variable a deployment sets — the name is written out because it does not always match the key upper-cased (`app.base_url` is `PUBLIC_BASE_URL`, and `app.assets_url` is `PUBLIC_ASSETS_URL`). `app.assets_url` names where the browser fetches static assets from: the built-in `/static` mount by default, and an S3 bucket or a CDN origin once a deployment points the variable there — one URL, no driver switch of its own. `log.transport` and `otel.endpoint` are directives, because a deployment is the one that decides whether it keeps the terminal, ships to a collector, or both, and where that collector listens; `log.file.filename` does not exist at all, so there is nothing to pin. A list key written as a directive arrives as one string, because that is all an environment variable can carry, so `internal/config/lists.go` holds `listKeys` and `normalizeLists` splits it (`LOG_TRANSPORT=console,file,otlp`); without that step koanf would decode the string into a one-element list holding "console,file,otlp", which names no sink. A test asserts `listKeys` is exactly the set of slice-valued fields on `Config`, the way the duration test asserts `durationKeys`. The same file holds `mapKeys` and `normalizeMaps` for a key whose value is a map (`otel.headers`), split from the specification's own `name=value,...` form, and the same test asserts it against the map-valued fields. A map key is also kept whole by `flattenNested`, so a **file** writes it as a JSON object rather than as a section: walking it would produce `otel.headers.authorization`, a key that is not part of Config, which `filterKnown` would drop — leaving the header silently unset instead of reported. Space is not a separator: `console file otlp` stays one name and is then refused by name, rather than being read as three sinks nobody asked for. An entry with no `=` is dropped rather than sent as a nameless header, while an empty value (`x-empty=`) is a header with no value, which is legal.

`mailer` is the optional email section: an empty `mailer.smtp_host` means the mailer is not configured and is **not** a configuration error, so a local checkout needs no mail server. `Validate` checks only what a set host needs — a usable port, an address in `from_email`, and a username whenever a password is given (`mailer.smtp_password` is a secret, so `Redacted` hides it and `Sample` writes it as a directive). An unset variable is reported only where it leaves the key unusable (`Config.unsetNote`), never for every key that references one: an unset `APP_MODE` falls back to development and `auth.private_key` to the HMAC secret, so reporting those would flag a deliberate choice. Driver and format values are `memory`/`kvstore` (cache), `database`/`kvstore` (rate limit, session), `pretty`/`structured` (log), `local`/`s3` (storage); a key-value backend is named `kvstore` rather than after the product behind it. `storage.s3` holds the object-storage settings, nested rather than flattened because its eight keys cover credentials, the bucket, the endpoint, the addressing style, a prefix, a region, and a link lifetime — a common prefix on each would be noise the nesting already carries. The section is validated **only when `storage.driver` is `s3`**, so a local deployment that keeps credentials in the file for a later switch still runs. `storage.s3.region` has a concrete default (`DefaultS3Region`, `us-east-1`) rather than an empty one because the S3 client refuses to resolve an endpoint without a region and every request fails — even against a service that ignores the region such as MinIO — so an unset `STORAGE_S3_REGION` variable must leave a usable value; an explicitly empty region is still an error. `signed_url_expires` is a duration key, and Validate holds it inside `1s..7d`: the protocol caps a signed link at seven days, and the client reads a zero as "use my own fifteen-minute default" rather than as a lifetime. `force_path_style` defaults to true because MinIO and Silo need it and the client does not fall back on its own (`bucket.localhost` does not resolve). The credentials are in `secretKeys`; their variable names are what `EnvName` derives, so they are deliberately **not** in `envKeys` — that map is for a name that differs from the derived one. `path_prefix` is in `nullKeys`, so a generated file writes `null` rather than `""`; the two resolve alike, so this is about what the file reads like.

`log` holds the console settings plus the two optional sinks, selected by `log.transport` — a list of `console`, `file`, `otlp` — which is the one place a sink is switched on. The default is `[console]`, so a fresh checkout and a container that logs to stdout need no volume and no collector. `Validate` refuses a name no sink matches, a repeated name, and an empty list, and checks a section **only when its transport is named**: the rotation keys of `log.file` are read then, and `log.console.format` likewise (the way `storage.s3` is read only on the `s3` driver), including the one combination that never deletes a rotated file (`max_backups` and `max_age` both zero, which would fill a disk quietly), and `log.otlp.path` is held to a path then. `log.file` has no filename key: the sink writes to `storage.local_path + /logs` + `tango.log`, so the process has one data directory.

`otel` is the section the three signals share, and its shape follows from one decision: **one collector address serves logs, traces, and metrics**, because that is what a collector is, so `otel.endpoint` is the only place a collector is named. A signal that needs a different route on that collector sets its own path (`log.otlp.path`, `otel.tracing.path`, `otel.metrics.path`), never its own address — a second address would be a second configuration source deciding where telemetry goes. `otel.endpoint` has a concrete default (`DefaultOTLPEndpoint`, `http://localhost:4318`, the protocol's own port) rather than an empty one, so an unset `OTEL_ENDPOINT` leaves a usable address instead of blocking a deployment whose collector is local, and its scheme is what decides TLS, so there is no second setting to keep in step with it. `otel.service_name` defaults to the application identifier rather than to an empty string, because a record with no service name cannot be attributed at all. `otel.protocol` is shared by the three signals for the same reason the address is: a collector accepts one protocol per listener, so a deployment that needs two is running two collectors, which is what a second address would be. The value is spelled the way the specification spells it, and the endpoint is held to the form the chosen protocol addresses: a URL for the two HTTP protocols, host:port for gRPC. **`grpc` reuses `otel.endpoint`** — the exporter is addressed by host and port, so `CollectorEndpoint` reduces a URL to its host and port and `CollectorSecure` reads TLS from its scheme, which is what keeps one address serving both forms. Switching the protocol without moving the address is refused by name (`DefaultOTELHTTPPort`), because the two protocols are two listeners of one collector: `otel.protocol: grpc` with the default `http://localhost:4318` looks applied and ships nothing. **`http/json` is refused for metrics and logs**, because only the trace exporter encodes JSON in the Go SDK: the alternative is sending protobuf to a collector expecting JSON, which fails somewhere far from the key that caused it. `otel.headers` is a map and therefore in `mapKeys`, so it is kept whole at load time rather than walked into dotted keys `filterKnown` would drop — a JSON object in the file, and the specification's own `name=value,...` string behind a directive. Every header **value** is a secret (in `secretKeys`) because an authorization token is why the key exists and the names inside are chosen by the user; the names are kept in a rendering, since a name says which credential is missing without revealing it. `otel.tracing.*` is read only when `enable` is true, and `otel.metrics.*` likewise, the way `storage.s3` is read only on the `s3` driver: a signal nothing switched on is not held to a sampler or an interval it never runs. `otel.tracing.ratio` is read only by the two ratio samplers, so a ratio outside `0..1` is refused by name rather than silently ignored, and `otel.metrics.prometheus_path` is a **path** rather than a second enable flag: the exposition is always served when metrics are on, and where it is served is the one decision a scrape job needs. `otel.queue.max_size` bounds the in-memory buffer each signal exports from, which is the setting that keeps export off the request path.

`kvstore` is the optional Valkey/Redis section: `Enable` gates availability, while the per-feature driver fields still choose what each feature uses, so switching the backend on moves nothing by itself. `Validate` reports the one combination that cannot work — a driver set to `kvstore` while `Enable` is false — naming every offending driver in one message (`Config.kvStoreDrivers`), and checks `kvstore.url` **only when enabled**, since a disabled backend is never dialled. `isKVURL` mirrors the URL grammar the client accepts (`redis.ParseURL` in `redis/go-redis`: schemes `redis`/`rediss`/`unix`, a missing host defaulted to `localhost:6379`, a path that is empty or one integer database index, a unix socket carrying its path) — validation stricter than the client would reject a URL that connects, and mirroring the query-parameter list is not done because it is a second copy to keep in step. `RedactKVURL` reduces the URL to `host:port/database`; it does **not** reuse `RedactDSN`, whose parse is pgx's and rejects a `redis://` URL outright, which would replace the whole target with the placeholder. There is one data directory, `storage.local_path` — `app.data_dir` was removed rather than kept as a second path that could disagree with it. `secretKeys` is one list, asserted against both `Sample` and `Redacted`, so a secret cannot be written literally or reach a log line. `Config.Origin` reports which layer last set a key (`default` / `config-file` / `flag`).

Two secret renderings, deliberately kept apart, both built on `withSecrets`: `Redacted` replaces every secret with `[redacted]` and is the **fail-safe** behind `Config.String()`, so a log line never carries a fragment of a key; `Masked` keeps the first and last four characters with `****` between them, which is what `config:print` renders so a value can be traced to the key that produced it. A secret shorter than `maskMinLength` (16) is redacted in full even by `Masked`, because keeping eight characters of a short password would leave most of it readable; an empty secret stays empty so an unset key reads as unset. Neither renders the DSN: `RedactDSN` reduces it to `host:port/database`, the one rendering the CLI and the health check both use, because a connection string is a composite value where revealing part of the string says nothing. `config:print` renders the resolved configuration as a table (`github.com/rodaine/table`, coloured through `printext.Palette`): the values come from `config.Values(cfg.Masked())`, so a secret cannot reach the table even by mistake, and `--source` adds the layer from `Config.Origin`. It resolves with `configFrom`, **not** `fullConfigFrom`: a configuration being inspected is often one that does not validate yet, so an unset key prints empty rather than stopping the report. The table writes through `trimmedWriter` because rodaine/table pads the last column too, and the header is trimmed **before** it is painted — a colour reset is invisible but not zero-width, so trimming after it would leave the padding inside the escape where it survives into a redirected file. `cmd/config.go` resolves once in the root `Before` and puts the result on the context as a `configState` — the result *and* the failure, because resolution is **deferred**: a broken or absent config file must not stop `config:generate` (writes the file) or `key:generate` (runs before a referenced variable exists), so the command that needs the configuration is the one that reports the error.

### internal/fetcher

The outbound HTTP client. One `*fetcher.Client` is built in `internal/registry` from `config.Fetcher` and the process `*slog.Logger`, resolved when `serve` starts, and closed by the injector's shutdown. Features call `Do` with an absolute URL; they do not construct a client and there is no configured base URL — an upstream address is hardcoded at the call site. Hosts share one connection pool and each host owns a Resty client, because Resty's breaker is per client and `Allow` does not receive the request, so one breaker cannot tell hosts apart. Resty (`resty.dev/v3`, v3.0.0-rc.4) is the transport. Its debug log stays off, because that log includes bodies. A cookie jar is not installed, so one upstream's cookies are not replayed to the next. `RedirectHeaderStripSensitivePolicy` drops `Authorization` and `Cookie` on a redirect to another host. Each call starts a client span and injects W3C `traceparent` (and baggage) from `otel.GetTextMapPropagator`, falling back to trace-context plus baggage when the global propagator has no fields — that is the SDK default until `observer.SetGlobals` installs the same pair.

`Do` returns the response for an HTTP status of 400 or above and an `*fetcher.Error` a caller matches with `errors.Is`: `ErrNetwork`, `ErrTimeout`, `ErrCanceled`, `ErrCircuitOpen`, `ErrStatus` (the code is `Error.Status`), and `ErrRetryExhausted` alongside the class when every configured retry ran. The error text is method, scheme, host, and path. The query and the userinfo are omitted, and the transport error is not unwrapped into the text, because `url.Error.Error` contains the full URL. The response body is returned to the caller and is not logged. Resty's own lines go through an `slog` adapter that redacts bearer and basic tokens, `password`/`token`/`secret` query parameters, URL userinfo, and the query string.

Timeout, retry, and the breaker are one policy so they do not trip each other. `fetcher.timeout` is the budget of a single attempt (Resty's `SetTimeout`, which applies only when the caller's context has no deadline) and also the dial and handshake budget. The caller's context cancels the attempt and the backoff wait. Retries use Resty's capped exponential backoff with jitter between `fetcher.retry_wait` and `fetcher.retry_max_wait`. Resty's default conditions retry only a `url.Error` whose `Temporary` method is true and do not look at status codes, so the client adds a condition: network failures and per-attempt deadlines, HTTP 408 and 429, and 5xx except 501. Other 4xx are not retried. POST and PATCH are not retried either — Resty refuses non-idempotent methods unless told to, and this client does not tell it to. `fetcher.retry_count` is capped at 5. The count-based breaker (`NewCircuitBreakerCount`) opens on the same statuses, and only after more failed attempts than one call's retries (`circuit_failure_threshold` must exceed `retry_count`), so the retries of a single call cannot open it. It stays open for at least one attempt budget (`circuit_reset_timeout` is at least `fetcher.timeout`) and then allows one probe at a time. `fetcher.user_agent` defaults to `tango/<version> (+https://github.com/riipandi/tango)`: a product token, not a browser token. The generated file omits the key (`omittedKeys`), so a checkout keeps that token by absence. `fetcher.max_body_bytes` defaults to 16 MiB and is refused above 32 MiB. A relative URL is refused.

### internal/mailer

The outbound email path: `*Mailer` submits over SMTP and `*Templates` renders the React Email output embedded in the binary. One `*mailer.Service` pairs the two; `internal/registry` builds it from `config.Mailer` and the process `*slog.Logger`, and `serve` resolves it before the listener opens so a broken template fails the run rather than the first send. The mailer is optional and stays so: an empty `mailer.smtp_host` builds a mailer whose `Send` reports `ErrNotConfigured`, which is not a deployment failure. `github.com/emersion/go-smtp` is the protocol and `github.com/emersion/go-sasl` the mechanisms; both are dependencies of each other, so adopting one adopts the pair.

A session is opened per `Send` and closed by it — no pool, because an SMTP session is stateful and a pooled one would have to be verified before reuse anyway. Encryption is decided once: `mailer.smtp_secure` selects implicit TLS (the port-465 shape, `tls.Dialer`), otherwise the connection is upgraded with STARTTLS when the server advertises it and sent in the clear when it does not — the local Mailpit server is the second case, and it is reported as a warning rather than refused, so a development checkout needs no certificate. The certificate is verified against the configured host, and TLS 1.2 is the floor. Credentials are presented with PLAIN where the server offers it and LOGIN otherwise; a server offering neither is `ErrAuth`, not a silent unauthenticated session. `mailer.timeout` bounds the dial, the handshake, every command, and the message body — the library's own defaults are RFC 5321's five and twelve minutes, far longer than a submission this process makes should take. A cancellation closes the connection through `context.AfterFunc`, so a blocked read fails instead of waiting out the server.

The library exports no sentinel for "this server has no STARTTLS", so the plaintext fallback matches its message text (`startTLSUnsupported`); a test runs that message against a Mailpit container, so a library change fails a test rather than quietly moving a session to plaintext. A failed STARTTLS attempt closes its own connection, so the fallback dials again — only a server without TLS pays for the second dial.

`Message` is what the caller supplies and `envelope` what the session needs: the sender, every recipient including the blind ones, and the RFC 5322 bytes. A message with both bodies is `multipart/alternative` with the text part first, so a client that cannot show the HTML falls back to the plain one; a message with one body is sent as that body alone, because a wrapper around a single part is boilerplate some readers display. Headers and bodies are quoted-printable, the subject and the sender name are RFC 2047 encoded words, and every line is CRLF terminated. `Bcc` is an envelope recipient only — it is never written into the headers, which is what keeps it blind. An address or header value carrying a line break is refused, because the envelope is written line by line and that is the injection. A `Message-ID` is generated per message from a random identifier at the sender's domain.

`Templates` parses the compiled files (`web/email/*.tmpl`, embedded through `web.EmailTemplates`) at construction, as pairs: a name with only one rendering fails construction, and an unknown name is refused by `Render` rather than producing an empty body. The two renderings are separate template sets on purpose — `html/template` escapes what it writes and `text/template` does not, so the HTML body is safe against a template field carrying markup while the plain-text body keeps the characters as written. Every template's field set is a struct in `data.go` (`PasswordResetData`, `LoginNewDeviceData`, …): a template naming a field the struct lacks fails the render, so a renamed field is caught by a test rather than printed as nothing. A struct is used rather than a map because the field name is then checked at the call site too. `LoginNewDeviceData.DateTime` is the one `time.Time`, because that template formats it itself; every other date is a string, because these values travel the queue as JSON. `SenderFrom` resolves the sender identity from `app.assets_url`, so a template's logo follows the deployment's asset origin and the URL is a real asset rather than a `{{.LogoURL}}` that nobody filled in.

`cmd/mailersmoke.go` is `mailer:smoke`: it renders one template and submits it through a real server, printing the server, sender, auth, TLS mode, template, and recipient — the same shape as `logger:smoke` and `otel:smoke`, so the three prove their paths the same way. It builds the mailer itself rather than reaching for the registry, because a command that exists to diagnose mail should not fail before it can say which part broke.

### internal/kernel

The module contract. A `Module` is `{Name, Mount(chi.Router)}`: it owns its package and registers its endpoints through `Mount`, so no route list outside the module can drift from its handlers. `kernel.Mount` walks the modules a composition root passes; the transport serves what it is given, so a new module needs no change outside `internal/registry`.

### internal/transport

The HTTP surface, on chi. `NewRouter` composes the pipeline: request id first (every response and envelope metadata names its request), then the request logger and panic recovery (one line per request at the status's level — 5xx error, 4xx warn; a panic becomes a 500 envelope plus a logged stack), CORS (a policy question is answered before a route runs), and the request timeout (a context deadline the handler honours), then the endpoints — the `/api` landing endpoint, `/api/healthz` from `internal/health`, the metrics exposition at `otel.metrics.prometheus_path` when the signal is on, the feature modules' routes, and the SPA mount (`web.SetupStatic`, debug/release variants) last, because its handler answers whatever the routes above it did not claim and its own not-found rule keeps API and protocol paths from being answered with `index.html`. Request ids are TypeIDs with the `req_` prefix (`go.jetify.com/typeid`), honoured from the incoming `X-Request-Id` header and stored through `responder.WithRequestID`, so middleware, envelope metadata, and a later trace agree on one idiom. CORS is `rs/cors` driven by the `server.cors` section; an empty origin list is a passthrough, and `Validate` refuses `*` with credentials because the browser does. The rate limiter throttles the `/api` surface only — a static asset or a metrics scrape spends no check — and is refused-with-429 through the responder envelope, whose metadata reads the `X-RateLimit-*` headers the middleware writes; a limiter that cannot answer lets the request through, because a degraded protection is not a downed service. Paths that must never be throttled — the health endpoint, a probe — are the hardcoded prefix list `rateLimitExclusions` in `internal/transport/handler.go`, one entry per line with its reason, matched against the request path before the check runs. The limiter's driver is chosen in the registry: `database` runs `fn_check_rate_limit` (the fixed window is synchronized under advisory locks in migration `00007`, and the raised `42901` SQLSTATE is read as the result, its detail carrying the retry hint), `kvstore` runs one Lua script on the shared backend (`tango:ratelimit:` prefix); the key is the client address sanitized to the alphabet the `rate_limits.key` check allows. Behind a proxy every key is the proxy's address — a trusted-proxy setting is a later decision, not a spoofable `X-Forwarded-For` read. `NewServer` binds the timeouts; the listener and the graceful drain stay with `serve`.

### internal/registry

The composition root. `New(ctx, cfg, metrics, logger)` registers the shared services with samber/do (config value, the logger and metrics handler as values, the single `datastore.Postgres` pool, the health checker over it, the Valkey client and cache when enabled, the queue client with `internal/jobs` registered on it, the rate limiter, the router, the server) and returns the injector; services are lazy, so resolving the server is what opens the pool and an unreachable database fails the run before the listener opens. The metrics handler and the logger are built and closed by the command lifecycle, not by the container — registered as values, so the services below resolve them like any other dependency instead of receiving them through a second channel. `serve` starts the queue before the listener opens and closes the injector after the drain — the pool and the workers outlive the listener.

**Every query against application tables is built with `go-sqlbuilder`** (PostgreSQL flavor), not written as a raw string: the queue store, the scheduler, the storage manifests, and the seeders all follow the same shape — builder → `Build()` → the shared `Querier` — so one place owns the placeholder dialect and a query can never smuggle a value into the statement by hand. Raw SQL is the exception in two places only: tests (assertions and fixtures may write plain `$1` strings) and `database/`'s maintenance tooling, whose statements are the migrator's own bookkeeping or the server's deparse output. A `SELECT` of a database function is still a query — `fn_check_rate_limit` is built with `sb.Var(...)` like any other argument.

## Library decision records

Outcomes of library comparisons, kept so the comparison does not get re-run. Record a new outcome here when it settles a decision.

- **Look up before writing against a third-party package**: Context7 MCP (`mcp_context7__resolve_library_id`, then `mcp_context7__query_docs`) for API usage and options, DeepWiki MCP (`mcp_deepwiki__ask_question` with `owner/repo`) for design intent and behavior. Use them when the answer depends on a version, when the README is thin, or when comparing two candidate libraries. Do not use them for this repo's own code — read the source. The pinned source of truth is the module cache (`go env GOMODCACHE`); when docs and code disagree, the code wins — say so and follow the code.
- **In-memory cache**: deliberately avoids both cache libraries it was weighed against. `allegro/bigcache` does not handle hash collisions — the new item overwrites the previously stored one, a documented data loss — and `VictoriaMetrics/fastcache` would add `golang/snappy`, `golang.org/x/sys`, and `allegro/bigcache` (its benchmark peer) as runtime dependencies. The design was adopted instead: chunked byte ring, append-style `Get(dst)`, collision handling via full-key verification and a secondary slot. The hash is the stdlib `hash/maphash`, seeded per process; `cespare/xxhash/v2` is already in the module graph (goose, Prometheus) and stays indirect.
- **samber/hot** (studied 2026-09 as an improvement source for `internal/cache`): not adopted as a dependency — its generic `HotCache[K, V]` layer sits above per-value maps, which gives the garbage collector every entry to scan and loses the byte-ring zero-allocation property the in-memory driver is built around; its collision story is no stronger than the full-key verification already in place. Four ideas were adopted in design instead: the monotonic-clock expiry (an entry stores its deadline as an offset from a process-start baseline, read via `time.Since` — a wall-clock step can neither age an entry early nor resurrect it), batch operations on the `Cache` contract (`GetMany`/`SetMany`/`DelMany`, where the remote driver answers in one round trip — MGET, a pipeline of SETs, one DEL — while the in-memory driver loops over Get), and benchmarks pinning the zero-allocation claim (`cache_memory_bench_test.go`). Declined with reasons: lock-free reads (an in-place overwrite breaks concurrent readers; 64 sharded RWMutexes keep contention low already), TTL jitter and janitor (a janitor contradicts the settled "no flush goroutine to stop" decision; jitter stays an option if synchronized expiry ever bites in practice), cache hit/miss metrics (belongs in `internal/observer`'s bridge when a real dashboard needs it), and stale-while-revalidate / loader chains / missing-key caching (these need a typed layer above the byte contract and goroutine lifecycle — a feature-layer concern to build over the queue/scheduler when a feature asks for it, not a driver property).
- **Key-value client**: `valkey-io/valkey-go` over `redis/go-redis/v9` for the same economy: valkey-go brings no runtime dependency beyond `golang.org/x/sys` (already in the graph), parses the `redis://` URL scheme itself via `valkey.ParseURL`, and the `isKVURL` validation mirrors its grammar.
- **Scheduling and concurrency libraries** (`go-co-op/gocron/v2` — runtime deps `jonboulle/clockwork` + `robfig/cron/v3`; `alitto/pond/v2` — zero deps): left out. Neither is a queue — both hold everything in memory, so neither can replace `internal/queue`'s durable claim/retry/archive over Postgres, and a process death loses every in-flight task. Recurring jobs need no gocron either: a job that enqueues its own next instance is durable, multi-process safe through the queue's atomic claim, and inherits retries, backoff, and archive — what an in-process scheduler provides only behind an elector or locker that has to be implemented and run somewhere. Revisit gocron only when cron-expression schedules (daily at a time, monthly) become a real requirement, and even then the durable shape is a cron parser that computes the next run and enqueues it as a task, never business logic running in-process.
- **River** (`riverqueue/river`): a mature Postgres queue, evaluated and left out — adopting it would replace `internal/queue` wholesale — its own schema (`river_job`, `river_job_state` enum, `river_leader` election, `river_migration` versioning), its own client/worker idiom, and a dependency set beyond pgx (`pgerrcode`, `puddle`, `tidwall/gjson`+`sjson`, `x/sync`) — for features tango has not asked for. The parts that would tempt later are a paid Pro subscription ($125/mo, private module): workflows, batching, sequences, concurrency limits, dead letter queue, durable periodic jobs (`Pilot` persistence), encrypted jobs, ephemeral jobs. Its periodic-job shape validated the `internal/scheduler` design instead: a `Next(time)` schedule interface with robfig/cron plugged in as the implementation, an atomic claim so exactly one replica triggers a tick (River runs the enqueuer on an elected leader; a CAS claim on `scheduler_jobs` needs no election), and claim + enqueue in one transaction. Worth porting when a real need appears: unique jobs via a partial unique index, and queued-task cancellation.
- **Outbound HTTP client** (`resty.dev/v3` v3.0.0-rc.4): adopted for `internal/fetcher` because the integration client needs attempt timeouts, capped exponential backoff with jitter, a count-based circuit breaker, and a logger hook in one library. It is a release candidate; the pin stays on the rc that was read against (`SetTimeout` does not use `http.Client.Timeout` and does not apply when the caller already set a deadline; default retry conditions do not include 5xx or non-temporary network errors, so those conditions live in this repo). The cookie jar and the debug body log are left off. Revisit the pin when v3 leaves release candidate.
- **SMTP client** (`github.com/emersion/go-smtp` v0.25.0 + `github.com/emersion/go-sasl`): adopted for `internal/mailer` because it is the maintained Go SMTP client with STARTTLS and implicit TLS, a `Client` whose timeouts are settable, and an `io.WriteCloser` DATA command — one library for the session shape this repo needs, and it pulls in only `go-sasl` (which it uses for the mechanisms). `net/smtp` in the stdlib is frozen and carries no STARTTLS helper and no submission timeout. Two of its behaviors are load-bearing here: `NewClientStartTLS` returns an unexported error for "this server has no STARTTLS", so the plaintext fallback matches the message text and a test pins it against a container; and the STARTTLS handshake sends its own greeting, so a STARTTLS session introduces itself with the client's default name rather than the sender's domain (a plaintext session is greeted explicitly with `Hello`).
- **LogLayer transport pins**: `go.loglayer.dev/transports/otellog/v3` v3.0.0 was built against `go.opentelemetry.io/otel/log` v0.19.0, where `Record.Body()` returns `otellog.Value` and attributes are `otellog.KeyValue`. OTel moved `KeyValue` and `Value` into `go.opentelemetry.io/otel/attribute` in `otel/log` v0.20.0, so the transport does not compile above v0.19.0 (`undefined: otellog.StringValue`). `go.opentelemetry.io/otel/exporters/otlp/otlplog/otlploghttp` and `go.opentelemetry.io/otel/sdk/log` are held at v0.19.0 for the same reason: their `otel/log` floor has to agree with the transport's. The core module (`go.opentelemetry.io/otel`, and `otel/sdk` with it) is on its own version line and stays free, and so are the trace and metric exporters (`otlptracehttp`, `otlpmetrichttp`, `exporters/prometheus`), which depend on the core module rather than on `otel/log`. Before bumping any of the three pinned modules, check that the transport still compiles; the failure is at the type level and shows up only when `otellog` is built. **`go get` on an unrelated OTel package will silently raise `otel/log` past the pin** — it happened while adding the metric exporter — so after any `go get`, re-check the three versions and `go mod edit -require` them back.
